## 1. Outcome

The existing production Supabase Auth account `theuniquelizbeth@gmail.com` gains two capabilities:

1. The ability to create and manage student accounts through the already-built admin UI.
2. The ability to read all curriculum content.

This plan states plainly, and asks the reader to hold in mind through every section that follows, that these two capabilities are delivered by two entirely different, unrelated mechanisms in this codebase, and that the request as commonly phrased ("make her an admin") delivers only the first of the two automatically. ## 3. Repository findings (evidence)

**A1 — There is no admin role distinct from owner. This is the central finding of this plan and must be stated plainly and early.** The entire admin-tier authorization surface in this codebase is one function: `src/lib/ownerSettingsAuthorization.ts:65-66`, `export function isOwnerUser(user) { return user?.app_metadata?.role === 'owner'; }`. It is binary. There is no role hierarchy, no roles table, no permissions column, no profile table carrying a role, and no RLS policy anywhere that references `app_metadata` or any role claim for content access. `src/__tests__/ownerSettingsAuthorization.test.ts:29` explicitly asserts that `app_metadata: { role: 'admin' }` returns FALSE — a distinct "admin" value is already tested as unauthorized in this codebase. "Promote to admin," in this codebase, therefore means exactly one thing: grant full owner parity. There is no lesser tier available to grant.

**A2 — The same definition governs two surfaces.** `isOwnerUser` is re-exported, not redefined, by `src/lib/adminStudentAuthorization.ts:19`, so the owner-settings surface and the student-management surface share one authorization definition.

**A3 — Capability (1), create student accounts, already exists in full and needs no code change.** A complete owner-gated admin UI is already built and deployed: `src/pages/AdminStudentsPage.tsx` (roster, detail view, register/disable/delete/assign/unassign/wipe modals), `src/components/AdminShell.tsx`, `src/components/RegisterStudentModal.tsx`, `src/components/AdminStudentModals.tsx`, the service layer `src/services/adminStudentData.ts`, and the deployed Edge Function `supabase/functions/admin-student-operations/index.ts`. Each entry point is gated by the same `isOwnerUser` check: `AdminStudentsPage.tsx:63`, `AdminShell.tsx:20`, `App.tsx:52`. Student creation is the function's `register` action: `admin-student-operations/index.ts:125-126` dispatches to `handleRegisterStudent` at `:164-206`, which calls `serviceClient.auth.admin.createUser({ email, password: tempPassword, email_confirm: false })` and returns a one-time temporary password. Consequence: granting the owner claim delivers capability (1) immediately, with zero code change and zero new authorization surface.

**A4 — The real server-side boundary is the Edge Function, not the React check.** `admin-student-operations/index.ts:100-107` re-verifies the bearer token via `callerClient.auth.getUser(accessToken)` and then calls `isOwnerUser(userData.user)`, returning HTTP 403 otherwise. `supabase/functions/owner-settings/index.ts:80` does the same. All writes then go through a separate service-role client (`index.ts:119-121`) that the browser never receives. The client-side `isOwnerUser` calls are UI routing convenience only. This is a sound defense-in-depth design and this plan does not change it.

**A5 — Capability (2), see all content, is NOT granted by the owner claim. This is the most important correction this plan makes to the user's mental model, and it must not be softened.** Verified directly against `supabase/migrations/202607200002_admin_student_rls_hardening.sql`: all four entitlement policies key exclusively on `student_enrollments`, `public.is_account_active(auth.uid())`, and unlock-date arithmetic. None of the four references any role claim. Specifically: lessons, `:19-32` (active enrollment in the band, not unlock-gated); resources, `:36-56` (active enrollment AND `now() >= se.enrollment_date + make_interval(days => l.unlock_offset_days)`, OR a completed enrollment); `storage.objects`, `:60-81` (the same predicate, correlated to a visible `resources` row via `r.storage_bucket = storage.objects.bucket_id and r.storage_path = storage.objects.name`); `student_enrollments`, `:86-93`. This independently reconfirms finding J-014 already recorded in the deploy-safety plan: the owner role carries no RLS bypass to gated content. The only bypass predicate present on any of these tables is `auth.role() = 'service_role'`, which is never true for a browser-signed-in user.

Stated plainly: an account with `role: 'owner'` and no enrollments sees an empty roadmap and can read no lesson content at all. The two requested capabilities are served by two entirely separate mechanisms, and a single "make her an admin" action does not deliver both.

**A6 — The execution channel already exists and is backup-gated.** `scripts/set-owner-role.ts` is the established, precedented, guarded path for exactly this mutation. It was built for the deploy-safety plan's gates G9b.2/G9c.2 precisely because only a scripted path can be constrained by `scripts/require-backup.js` chaining (deploy-safety plan finding J-016, Hole 1: a Dashboard click cannot be gated). Its existing guards: refuses any `@test.local` email (`:76-94`); refuses the fixture owner UUID `00000000-0000-0000-0000-000000000099`, both before and after lookup (`:87-92`, `:223-226`); refuses to run against the local stack unless `SET_OWNER_ROLE_ALLOW_LOCAL=true` (`:124-139`); requires `SUPABASE_SERVICE_ROLE_KEY` from the environment with no hardcoded fallback (`:147-155`); merges rather than replaces `app_metadata` so `provider`/`providers` survive (`:102-107`, `:232`), which matters because clobbering them breaks GoTrue authentication; and prints only a safe summary, never the key or the raw user record (`:262-272`). Invocation precedent: `node scripts/require-backup.js --gate <G> && npx tsx scripts/set-owner-role.ts <email>`.

**A7 — Blocking defect: running `set-owner-role.ts` as-is for a second owner causes a real, user-visible production regression. This is the single most consequential finding in this plan and the reason it is not a one-line data change.** `applyOwnerRole` does two things, not one: it merges the role claim (`:234-239`) AND unconditionally upserts an `owner_settings` row keyed on `owner_id` (`:241-252`) with hardcoded brand/copyright/IP-notice constants (`:54-63`). `public.owner_settings.owner_id` is `not null unique references auth.users(id)` (`supabase/migrations/202607170001_init_schema.sql:81`) — unique per owner, not globally single-row — so a second owner produces a SECOND row rather than a constraint error.

The read path, `src/services/ownerSettingsData.ts:92-111` `getOwnerBranding()`, issues an unfiltered `.from('owner_settings').select(...).maybeSingle()`. `maybeSingle()` errors when more than one row is returned. The read policy `authenticated_read_owner_settings` is `using (true)` scoped `to authenticated` (`supabase/migrations/202607250002_fix_bands_owner_settings_read_scoping.sql:32-37`), so EVERY signed-in user, including every student, sees both rows. The function catches the resulting error (`:103-105`) and silently returns `toBranding(null)`, the default branding.

Net effect for every signed-in user: the site's brand name reverts to the default, and, more seriously, the lesson-page IP/legal notice reverts to the unconfigured placeholder text containing the literal string `[Instructor/Company Name]` (`ownerSettingsData.ts:32-39`). Conclusion: the script must not be run unmodified against this account. A narrow, reviewable change is required, adding an opt-out (for example `--skip-owner-settings`) so a second grant applies only the role claim and creates no second settings row. This is gate G14.1 below.

Recorded as an open item this planning pass does not settle: with two rows present, which of the two rows the `owner-settings` Edge Function's WRITE path updates is not established here and must not be assumed.

## 4. Research evidence

`RESEARCH_EVIDENCE` packet received from the nested Researcher, 8-entry source ledger, official Supabase documentation only, accessed 2026-08-03. Confidence levels and the three stated gaps are recorded here honestly; the gapped items must not be treated as settled in execution.

**R1 (HIGH).** `app_metadata` is server/admin-controlled. The end-user client API `auth.updateUser` accepts only email, phone, password, `data` (= `user_metadata`), and nonce; `app_metadata` is not an accepted attribute there. Writing it requires the admin API with the service_role key, documented as server-only. By contrast, `user_metadata` is "editable by the user without any checks," and Supabase explicitly warns against using it in RLS or authorization logic. The codebase's choice of `app_metadata` for the owner claim is therefore the correct choice and this plan affirms it. Sources: `reference/javascript/auth-updateuser`, `auth-admin-updateuserbyid`, `guides/auth/users`.

**R2 (HIGH).** Default hosted access-token (JWT) lifetime is 1 hour. Refresh tokens are single-use with a 10-second reuse window; reuse outside that window terminates the session and revokes its tokens. Source: `guides/auth/sessions`. This plan does not assume the default applies to this project; the actual configured value must be confirmed, not assumed, before the rollback procedure in Section 12 is relied upon.

**R3 (HIGH).** A grant does not propagate to an already-issued access token. The official reference for `auth.admin.updateUserById` shows the change followed by a client call to `refreshSession()` so listeners are notified with the updated user; there is no documented push mechanism. Operational consequence: after the grant, the account must refresh its session, or sign out and back in, before the admin UI appears.

**R4 (HIGH, and it constrains the rollback design in Section 12).** Sign-out revokes REFRESH tokens, not access tokens. Supabase states plainly that "there is no way to revoke a user's access token jwt until it expires." `auth.admin.signOut(jwt, scope)` and `auth.signOut(scope)`, with scope `global` / `local` / `others`, are the documented invalidation APIs; on sign-out, sessions are removed from the database entirely. Sources: `reference/javascript/auth-signout`, `auth-admin-signout`, `guides/auth/sessions`.

**R5 (HIGH).** `auth.getUser()` "performs a network request to the Supabase Auth server, so the returned value is authentic and can be used to base authorization rules on," unlike the local/cached `getSession()`. Source: `reference/javascript/auth-getuser`. This is why the Edge Function check described in finding A4 is the real security boundary.

**GAP G1 (not documented).** Whether a refresh-token exchange re-reads `app_metadata` fresh from the database to mint new claims, or copies forward the prior token's claims, is not stated in official documentation. This must be resolved empirically, not assumed, and gate G14.5 (case T1) exists for that purpose.

**GAP G2 (inferential, not stated as an explicit sentence).** No official source states outright, in one sentence, that a user cannot write their own `app_metadata`. R1's boundary is established by the union of the admin-only write path and the user API's accepted-attribute list. This is a strong inference, not a direct quotation, and gate G14.5 (case T4) closes it empirically.

**GAP G3 — the decisive unknown in this plan.** It is not documented whether `auth.getUser(jwt)` returns database-fresh `app_metadata` or the claims embedded in the token at mint time, nor whether it rejects a token whose `auth.sessions` row has been deleted. This determines whether a revocation takes effect on the server immediately, or only after the outstanding access token expires. It must not be assumed in either direction. This plan resolves it by empirical test at gate G14.5, case T3, and, until that test has run, the rollback runbook in Section 12 assumes the WORSE case (revocation is not immediate).

## 12. Rollback / revocation procedure

Required by the job brief and written here as an executable runbook, not a sentence.

**Added, 2026-08-03, `PLAN_DUCK` judge-remediation pass (J-001). This procedure restores CONTROL, not DATA.** A reader consulting this section alone must not be misled: revoking the role claim and terminating sessions stops FUTURE use of the admin surface by this account. It does not undo any destructive action already taken through it. Per finding A7 there is no RLS bypass anywhere in this system that could restore a hard-deleted `auth.users` row (with its cascaded `student_enrollments` and progress data, `admin-student-operations/index.ts:302`) or a `student_enrollments` row removed by wipe-save (`:470-473`). Per new finding A12, this system has no audit log, so a destructive action taken before rollback also cannot be attributed after the fact. The only genuine recovery path for data already destroyed is the Path B backup precondition already required by gates G14.3 and G14.4: a MANUAL, POINT-IN-TIME `supabase db dump` snapshot taken before those gates run. It permits reconstructing data destroyed BEFORE the snapshot's moment; it does nothing for a destructive action taken during normal operation afterward. This project's billing tier, and therefore whether any automatic backup or PITR exists beyond that manual snapshot, is unverified; see finding A11 point 1 and next action N-1 in Section 16. No automatic recovery should be assumed to exist.

1. Remove the `role` key from the account's `app_metadata` via the service-role Admin API, using the same merge-not-replace discipline established in finding A6, so `provider`/`providers` survive.
2. Immediately call `auth.admin.signOut(<jwt or user>, 'global')` to terminate sessions and revoke refresh tokens.
3. If Decision D3's enrollment option was used, set the enrollments to `preserved` rather than deleting them, matching the non-destructive precedent already used for the smoke account at the deploy-safety plan's gate G9c.4.
4. Re-assert that `owner_settings` still has exactly one row.
5. Verify by empirical test that the account can no longer invoke the admin Edge Function.
6. **Residual access window (corrected 2026-08-04, T2 remediation of G14.5's evidence; supersedes the prior overclaimed entry below).** G14.5's own required test for this question (case T3: hold a still-unexpired access token issued BEFORE revocation, revoke, then immediately call the admin Edge Function with that same token and record whether it is denied) was never actually executed in either of the two G14.5 attempts. What WAS confirmed is only that the database row itself updates immediately when the role claim is removed via the Admin API — a narrower and less consequential fact. Whether an outstanding, still-valid access token is actually rejected by the Edge Function's authorization check before its natural expiry remains empirically UNTESTED (gap G3 is still open). Per gap G3's own instruction in Section 4, this procedure must therefore assume the WORSE case rather than the favorable one: **treat an outstanding access token issued before revocation as potentially usable through the admin Edge Function for up to its full remaining lifetime (up to the configured token lifetime, default 1 hour per R2)**, not as immediately blocked. Operators executing this rollback should treat the window between revocation and the token's natural expiry as a genuine residual exposure window, not a closed one, until the actual Edge-Function-with-pre-revocation-token test is performed and recorded.
