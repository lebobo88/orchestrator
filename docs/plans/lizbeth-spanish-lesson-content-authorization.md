## 1. Outcome

Lesson body content for all 78 weeks stops shipping in the public production JavaScript bundle. It is instead delivered only to an authenticated user who has an active enrollment in the lesson's band and whose week has passed its unlock date, using the same authorization model that already governs `resources` (student handouts, instructor decks, flashcards, vocabulary review). The visible behavior for an authorized student is unchanged: the lesson body still renders. The change is entirely in where the content lives and how it is fetched.

Audience for this outcome: the owner-operator, who currently ships the full curriculum text to every visitor's browser regardless of login state, and the engineering agent that will implement the fix.

## 3. Repository findings (evidence)

All findings below were independently verified by the Planner during this planning task, by direct inspection of the cited files and lines.

**L1 — the exposure.** `src/content/lessonContent.ts:25-38` declares three `import.meta.glob<...>('./beginnerWeek*.ts' | './intermediateWeek*.ts' | './advancedWeek*.ts', { eager: true })` calls. Per official Vite documentation (Section 4, R-Q6), `eager: true` without a scoped `import:` option replaces the dynamic-import structure with static imports of the whole module namespace, which is not selectively tree-shakeable. All 78 week modules are therefore unconditionally emitted into the chunk containing the glob call.

**L2 — the finding that makes the fix tractable.** The content is structured, fully JSON-serializable data, not markdown and not JSX. `LessonContent` (`src/content/lessonContent.ts:68-76`) is `{ bandName, weekNumber, title, phraseGroups: PhraseGroup[], selfCheck: string[], quiz: QuizItem[], practice: PracticeActivity }`; `PhraseGroup` (`:47-55`) is `{ id, title, ruleBox, example, translationTask, dialectNote, badges: ContentBadge[] }`. Every field is a string, number, or array of the same. Verified against a real content module, `src/content/advancedWeek01.ts:13-76`, which is a single exported object literal with no functions, no JSX, and no imports other than the `LessonContent` type. Approximately 5-15 KB per week. Serialization to JSON is lossless.

**L3 — one production consumer, four test consumers.** `src/pages/WeekDetailPage.tsx:10,160` is the only production import of the synchronous loader. `src/components/LessonContentView.tsx:2` imports only the `LessonContent`/`ContentBadge` types and the `RHYTHM_SEGMENTS` constant, neither of which carries lesson bodies. Four test files import `getLessonContentSync`: `src/__tests__/lessonContent.test.ts`, `lessonContentLoading.test.ts`, `lessonContentGlobDiscovery.test.ts`, and `LessonContentView.test.tsx`.

**L4 — the in-app render is already gated; the bundle is not.** `WeekDetailPage.tsx:157-169` renders lesson content only inside the `available` branch, reached only after the RLS-gated `fetchResourcesForLesson` returns at least one row (`:70-77`). The defect is strictly that the raw bundle contains everything, not that the UI renders it to an unauthorized user.

**L5 — the reused gate, already live and independently verified.** `resources` is gated by `students_read_unlocked_resources`; storage objects are gated by `students_read_unlocked_lesson_assets`. Both are defined in `supabase/migrations/202607200002_admin_student_rls_hardening.sql:34-56` and `:58-81`. Both correlate on active enrollment, `public.is_account_active(auth.uid())`, and `now() >= se.enrollment_date + make_interval(days => l.unlock_offset_days)` or a completed enrollment. The storage policy authorizes an object only when a row in `public.resources` has `storage_bucket = storage.objects.bucket_id` and `storage_path = storage.objects.name` (`:71-72`). Both are live in production and were independently verified at the deploy-safety plan's G6 and G9a.

**L6 — CRITICAL constraint ruling out the obvious "add a column" approach.** `students_read_enrolled_band_lessons` (`202607200002:17-32`) gates `lessons` by active enrollment and band ONLY. It is deliberately NOT unlock-date-gated; `src/services/roadmapData.ts:84-89` documents this intentionally ("lessons are not themselves unlock-gated — only resources are"). A `jsonb` content column added to `public.lessons` would therefore be readable by any enrolled student for ALL 26 weeks of their band immediately on enrollment, strictly weaker than the resources gate. Research finding R-Q4 (Section 4) confirms RLS is row-level only and Supabase column-level security is GRANT-based and role-scoped with no per-row predicate, so a column cannot be gated more strictly than its row. Any table-based option therefore requires a NEW table with a NEW policy, not a column on an existing one.

**L7 — a direct, already-shipped precedent for the chosen mechanism.** `resource_type = 'flashcards'` stores `flashcards.yaml` as a private storage object. `src/components/ResourcesPanel.tsx:49-65` requests a signed URL via `getSignedResourceUrl`, `fetch`es it, and parses it client-side with `parseFlashcardsYaml`. The chosen mechanism (Section 7) is this exact pattern with a different payload.

**L8 — the signing function's failure semantics.** `src/lib/storageSigning.ts:190-213` `getSignedResourceUrl(client, bucket, path, ttl = 3600)` calls `client.storage.from(bucket).createSignedUrl(path, ttlSeconds)` with the anon-key client carrying the student's own session, and returns `{ ok: false, reason }` on any failure without distinguishing "locked" from "not found" (documented at `:183-188`), deliberately so a denial cannot be used to probe for existence.

**L9 — the single source of naming truth in provisioning.** `scripts/provision-lessons.ts:532-561` `resolveResourceNaming(entry, preserveLocalFixtures)` is used both by the write path (`provisionLessons`, `:744-766`) and by the verification expected-set builder (`buildExpectedResourceTuples`, `:577-588`). Adding one entry to the array it returns propagates automatically to both the write path and the deploy-safety plan's G9a exact-tuple assertion. This is why the provisioning change specified in Section 8 is small and structurally drift-proof.

**L10 — an existing precedent for generating, not just copying, a storage artifact.** `prepareStorageFiles` (`:785-849`) copies/derives each week's files into `supabase/storage-seed/lesson-assets/<band>/week-NN/`, including deriving `flashcards.yaml` from `flashcards.md` by extracting a fenced YAML block (`:824-843`). `uploadToStorage` (`:899-938`) then reads the whole week directory (`:913`) and uploads every file with `upsert: true` (`:927`), so a new file written into that directory is uploaded automatically with no change to the upload loop.

**L11 — the delete-and-reinsert re-run is verified safe for referential integrity only.** `provisionLessons` deletes all `resources` rows for a lesson and re-inserts them on every run (`:747-766`). A repository-wide search for `references public.resources`, `references resources`, and `resource_id` returns ZERO matches, so no foreign key or other table depends on `resources.id`. Lesson rows are upserted on `(band_id, week_number)` (`:715`), so lesson IDs are stable across re-runs. Re-running provisioning does not disturb `student_enrollments`, `auth.users`, or `owner_settings`. **Correction, 2026-07-26, judge-remediation pass (J-020).** This finding addresses referential integrity only. It does not address AVAILABILITY: between the delete and the subsequent insert, `students_read_unlocked_resources` has no row to permit for that lesson, so a concurrent entitled read during a re-run returns nothing for the affected lesson. The initial draft of this plan incorrectly let L11 stand as though it also covered this window; it does not. See G13.4 (Section 8) for the structural fix.

**L12 — LOCAL PARITY RISK, must be handled, not discovered later.** `prepareStorageFiles` and `uploadToStorage` both skip Beginner weeks 1-4 when `preserveLocalFixtures` is true (`:790-792`, `:904-906`), because `supabase/seed.sql` already seeds those four weeks as local fixtures. Those four weeks are exactly what the local quick-select fixture accounts exercise. Without an explicit fixture addition, the new content artifact would be absent locally for precisely the weeks developers test against.

**L13 — no schema migration is required.** `resources.resource_type` is unconstrained `text` (`supabase/migrations/202607170001_init_schema.sql:54`, a comment enumerating the four current values, with no CHECK constraint and no enum). A new value therefore requires NO schema migration.

**L14 — the new row must be excluded from the visible resource list.** `src/components/ResourcesPanel.tsx:14-19,68,78,101` keys display off a `RESOURCE_LABEL` map and falls through to rendering the raw `resource_type` string for an unrecognised type, so a new row would surface as a visible, mislabelled download row unless explicitly excluded.

## 4. Research evidence

Full `RESEARCH_EVIDENCE` packet received from the nested Researcher, source ledger of 12 entries, official Supabase, PostgreSQL, and Vite documentation only, accessed 2026-07-26. Confidence levels and stated gaps are recorded honestly below and must not be overstated in engineering execution.

**R-Q1 — MEDIUM-HIGH confidence. The single most load-bearing claim in this plan.** Supabase documents that `createSignedUrl` requires `select` permission on the `storage.objects` table, with no bucket-table permission needed. Corroborated by the official Storage helper-functions guide (`https://supabase.com/docs/guides/storage/schema/helper-functions`), which states a single SQL privilege such as SELECT is shared by multiple Storage actions and supplies `storage.allow_only_operation()` precisely so a policy author can narrow a SELECT-based policy to one Storage action. **LIMITATION, stated explicitly and must not be forgotten in execution:** the canonical JS reference page could not be fetched directly (HTTP 404 to the fetch tool, likely client-rendered) and was evidenced only through search summarisation, so this is not a verbatim-quoted primary source. This plan therefore requires an empirical negative test as a hard gate rather than treating this as closed by documentation. **Amendment, 2026-07-26, judge-remediation pass (J-019).** That empirical test is gate G13.6a (Section 8), which now runs on non-sensitive canary artifacts BEFORE any real lesson content is uploaded, not gate G13.8 as originally sequenced against the real artifacts after upload. With G13.6a in place, the correct characterization is that this documentation gap is closed EMPIRICALLY BEFORE EXPOSURE, which is materially stronger than the earlier draft's position. This is not the same as saying the gap is fully resolved by documentation; it remains medium-high confidence and documentation-gapped, and the empirical proof is what carries the load, not the Supabase documentation itself.

**R-Q2 — HIGH confidence.** Per `https://supabase.com/docs/guides/storage/serving/downloads`, signed URLs are signed with a dedicated internal key separate from the project's Auth JWT signing key and "remain valid until their expiry time regardless of any Auth key changes." Revoking a user's enrollment does NOT invalidate an already-issued signed URL before TTL expiry; the only documented revocation path is to contact Supabase support. A signed URL is a bearer credential for its TTL window. See Section 7's accepted residual risk and Section 12's risk register.

**R-Q3 — HIGH confidence.** Per `https://supabase.com/docs/guides/storage/cdn/fundamentals` and `https://supabase.com/docs/guides/storage/cdn/smart-cdn`: for private buckets, permissions are checked per user and each signed URL's unique `?token=` is a distinct cache key, so no cross-user shared-cache exposure is documented. However, a cached edge response "can continue to be served for the same signed URL until the CDN cache duration expires, even if the token in that URL has already expired." The upload-time `cacheControl` option governs browser cache only, not CDN edge duration. No official source makes an explicit affirmative "no cross-user exposure" guarantee.

**R-Q4 — HIGH confidence.** PostgreSQL's row-security documentation (`https://www.postgresql.org/docs/current/ddl-rowsecurity.html`) establishes RLS restricts which ROWS are returned, with column-level access a separate GRANT-based mechanism. Supabase's column-level-security guide states plainly that RLS "doesn't give you control over which columns they can access within rows," and column GRANTs are role-scoped with no per-row predicate. This confirms L6.

**R-Q5 — MEDIUM confidence, and essentially NEUTRAL to the mechanism decision.** No official source establishes a technical blocker to either a `jsonb` column read through PostgREST or a Storage object at a 5-15 KB payload. The choice among Options A/B/C in Section 7 is dominated by the authorization architecture, not by size or performance. This plan does not manufacture a performance justification for its recommendation.

**R-Q6 — HIGH confidence.** Per `https://vite.dev/guide/features`, glob imports are lazy-loaded and code-split by default; `eager: true` emits static imports of the whole module namespace, and tree-shaking is available only in the "Named Imports" pattern where a scoped `import:` option is also passed. Vite documents NO affordance for verifying that a module's content is absent from built output. This plan states explicitly, at G13.3, that a deterministic string scan of the built assets is the only available mechanism and is not a documented Vite feature.

**DESIGN_ROUTE**
- profile: compact
- reasons: Bounded brownfield change to one existing page. No new screen, flow, or component. Three narrow user-visible consequences only: the lesson body acquires a genuine asynchronous load, a content-fetch failure needs copy distinct from the existing "not authored yet" message, and a new internal resource row must not surface as a user-facing download.
- agents_required: design-generalist, design-reviewer
- prototype: forbidden
- model_tier: sonnet

**Reviewed `DESIGN_HANDOFF` from `design-generalist`**, revised once after an evidence-backed `NEEDS_REVISION`. Its binding requirements, carried here verbatim as engineering acceptance criteria and referenced by gate G13.6:

1. Fold the content fetch into `WeekDetailPage.tsx`'s existing single `load()` function, awaited alongside the resources fetch, before `available` is set. Do NOT render `available` progressively; that would require a new nested loading state, out of compact scope, and would break the current all-or-nothing transition that mounts `LessonContentView` and `ResourcesPanel` together with no layout jump.
2. **HIGH-severity engineering invariant.** `load()` wraps its entire body in one `try { ... } catch { setState({ kind: 'error' }) }` at `WeekDetailPage.tsx:100-102`. A naively folded-in content fetch would propagate a signing denial, network failure, or `JSON.parse` throw to that outer catch, producing the page-level `role="alert"` "Could not load this week. Please try again." state with the Resources panel and `IpNotice` never rendering at all. The content-fetch step (sign, fetch, parse) MUST be its own non-throwing unit: either a local try/catch around just that step, or a helper returning a discriminated result `{ status: 'success', content } | { status: 'not-authored' } | { status: 'fetch-error' }`, so a content failure can never reach `load()`'s outer catch and can never produce the page-level `error` state.
3. The `ViewState` `available` variant (`WeekDetailPage.tsx:23-29`, currently only `resources` and `bandName`) must carry content status as an independently updatable field: `content: { status: 'success'; content: LessonContent } | { status: 'not-authored' } | { status: 'fetch-error' } | { status: 'retrying' }`, patched in place so Retry transitions `fetch-error` to `retrying` to `success` or `fetch-error` without touching `resources` or `bandName`, without re-running `load()`, and without unmounting `ResourcesPanel` or `IpNotice`.
4. The `not-authored` versus `fetch-error` distinction must be a real code-path distinction: was a `lesson_content` row present in the already-fetched resources array at all, versus present but unreadable. Never a heuristic on error text. Preserve the existing "not authored" copy verbatim: "This week's in-app lesson content has not been authored yet. The resources below are still available."
5. New failure copy, exact: "This week's lesson content couldn't be loaded right now. Please try again. The resources below are still available." Retry button label: "Retry". Transient retry copy: "Loading your lesson content…".
6. The failure message and its Retry button are wrapped in ONE container carrying `role="status"` with class `week-detail-content-error`, matching `ResourcesPanel.tsx:107-114`'s existing `<div role="status">` convention exactly. Do not put the role on the paragraph alone. `role="status"`, not `role="alert"` — `role="alert"` is reserved in that file for the catastrophic whole-page failure.
7. The Retry control is a real `<button type="button">`, keyboard-reachable in normal document order, meeting the same 44px touch-target and AA contrast floors `src/__tests__/designSystemConsistency.test.ts:198-207` already enforces on `.resources-panel-retry`. Reuse `.resources-panel-error`'s existing token pairing verbatim; no new tokens, no new colors, no new type scale.
8. Add `role="status"` to the existing page-level loading paragraph at `WeekDetailPage.tsx:115` (`<p>Loading&hellip;</p>`). One-attribute change, required in scope, because this change lengthens an already-silent loading window and that paragraph is the sole state paragraph in the file without a live-region role.
9. Exclude the new row at the call site: `resources.filter((r) => r.resource_type !== 'lesson_content')` before passing to `<ResourcesPanel>`. It must never reach `RESOURCE_LABEL` lookup.
10. **Labelled consequence, expected behavior and NOT a defect.** The page-level `empty` versus `available` split runs on the UNFILTERED resources count (`WeekDetailPage.tsx:70-77`), so a week with zero resource rows that later receives a backfilled `lesson_content` row will render `available` with the Resources panel showing its own local "No resources published for this week yet." message. Not reachable in production today, since every production lesson has four resource rows, but reachable locally and after any partial provisioning.
11. No implementation term ("signed URL", "storage", "bucket", "JSON", "RLS") may appear in rendered copy.

## 7. The mechanism decision

This is the analytical core of the plan. Three candidates were evaluated.

### Option A (REJECTED) — a new `lesson_content` table with a new RLS policy

Genuinely viable and architecturally sound. Its real advantage over the chosen option, stated fairly: a PostgREST `select` re-evaluates RLS live on every request, so revoking an enrollment takes effect immediately, whereas a signed URL is a pre-computed time-boxed grant.

Rejected because it requires net-new SQL authorization surface duplicating a predicate that already exists and is already verified, on a live-provisioned production database, immediately before Publish. That is more to get wrong and more to independently verify, for a revocation property this application does not currently rely on anywhere else.

Record explicitly, per L6 and R-Q4: the superficially simpler variant, a `jsonb` column on `public.lessons`, is NOT available, because `lessons` RLS is band-scoped and not unlock-gated, and RLS cannot gate a column more strictly than its row. A reader who assumes "just add a column" must be shown why that is wrong before proposing it in execution.

### Option B (CHOSEN) — a private Storage object plus a matching `resources` row

Each lesson gains one artifact at `lesson-assets/<band>/week-NN/lesson-content.json` and one `resources` row with `resource_type = 'lesson_content'`, `storage_bucket = 'lesson-assets'`, `storage_path` as above, `name = 'Lesson Content'`. The frontend fetches it with the existing `getSignedResourceUrl`, then `fetch`, then `JSON.parse`, exactly as `flashcards` already does (L7, L8).

Why it wins, in order of weight:

1. **It adds ZERO new RLS policy.** Entitlement is enforced by `students_read_unlocked_resources` (the row is invisible without enrollment plus unlock) and `students_read_unlocked_lesson_assets` (the object cannot be signed without a matching visible `resources` row). Both are already live in production and already independently verified at the deploy-safety plan's G6 and G9a. The requirement that RLS correctness be independently verifiable is satisfied by reusing a policy that has ALREADY been independently verified, rather than by writing a new one that would have to be verified from scratch. Every alternative adds new authorization surface.
2. It reuses a proven end-to-end pattern (L7, L8) rather than inventing one. Lower risk is the explicit selection criterion for this decision.
3. The provisioning change is small and structurally drift-proof because `resolveResourceNaming` is already the single source of naming truth for both the write path and the verification path (L9), and `uploadToStorage` already uploads whatever is in the week directory (L10).
4. It is additive against existing production state. No table is created, no policy is altered, no migration is required (L13), and nothing depends on `resources.id` (L11).

**Accepted residual risk, stated explicitly rather than left implicit.** Per R-Q2 and R-Q3, an issued signed URL is a bearer credential valid to any holder until TTL expiry, with no early revocation, and a CDN-cached response for that same URL can outlive the token's own expiry until cache eviction. This risk is not new and is not increased in kind by this plan: it is already accepted today for the student handout PDF, the instructor PPTX, and the flashcards, which contain the same pedagogical material. Rejecting Option B on this basis while continuing to serve the PDFs the same way would be incoherent.

**Amendment, 2026-07-26, judge-remediation pass (J-019).** The policy shape underlying this entire mitigation argument, that `createSignedUrl` genuinely denies an unauthorized principal, is proven empirically before any real content is exposed, by gate G13.6a's canary artifacts (Section 8), not after upload as the initial draft sequenced it. See Section 4's R-Q1 and Section 12's "Failure hold" procedure for what happens if that proof fails.

**Recommended mitigation — Decision D-1, open, needs user confirmation at approval.** Issue the `lesson_content` signed URL with a SHORT TTL, 60 seconds proposed, rather than the 3600-second default used for the four user-initiated download types. The content URL is consumed immediately and programmatically on page load and is never handed to the user or reused, unlike a download link the student may click minutes later. A short TTL costs nothing in usability here and materially narrows the bearer-credential window. Keep 3600 seconds for the four existing download types. Implement this as an explicit TTL argument at the content call site (per `storageSigning.ts:190`'s existing `ttl = 3600` parameter), not as a change to `STORAGE_CONFIG.SIGNED_URL_TTL_SECONDS`, which other call sites depend on.

### Option C (REJECTED) — a new Edge Function performing a server-side entitlement check

It is the only option offering true per-request, non-cacheable, immediately-revocable access, and that should be stated fairly.

Rejected because it is the largest change: a third deployed function, service-role key handling in a new place, a new deployment gate mirroring the deploy-safety plan's G9d, cold-start latency on every lesson view, and, decisively, it would move entitlement logic out of Postgres and into hand-written application code, duplicating a predicate that Postgres already enforces correctly. That is a net weakening of the authorization story, not a strengthening.

Note honestly: Researcher gathered no dedicated evidence on Option C, so this rejection rests on architectural reasoning and the local evidence above, not on cited sources.

## 12. Risks and rollback

- **Highest risk: uploading real curriculum content to production before the access-control policy is empirically proven.** Identified as a genuine defect in the initial draft's sequencing (J-019, Section 6a): as originally written, G13.7 uploaded all 78 real lesson-content objects and rows before any empirical authorization test ran. See the "Failure hold" procedure immediately below for what happens if a defect is nonetheless found later.
- **Risk: G13.7's provisioning write to production resource rows.** Mitigated by the mandatory Path B dump with recorded SHA-256, by L11's verified absence of any foreign-key dependency on `resources.id` (referential integrity only, corrected 2026-07-26), by the upsert-then-delete-superseded write pattern required at G13.4 (eliminating the availability window identified at J-020), and by the fact that the operation is idempotent and re-runnable. Rollback is a re-run of provisioning, and in the worst case a restore from the G13.7 dump. Per the deploy-safety plan's S-K, the Free tier has no automatic backups and no PITR, which is exactly why the dump is structurally enforced.
- **Accepted residual: the signed-URL bearer-credential and CDN-cache windows** described under Option B in Section 7, mitigated but not eliminated by the proposed short TTL (Decision D-1). G13.6a proves the policy is correctly gated; it does not shorten the TTL window or reach into the CDN cache, which remain accepted residuals per R-Q2 and R-Q3.
- **Risk that the dist-scan guard produces a false negative through an unsampled week.** Corrected 2026-07-26 (J-021): the initial draft's three-band sampling was insufficient, since a residual import of an unsampled week could ship raw content undetected. Mitigated now by requiring one fingerprint per week, all 78, and by requiring the guard to be observed failing against a pre-fix build with that failure confirmed to catch the specific weeks present (G13.3).
- **Risk of local-dev breakage for Beginner 1-4**, addressed by G13.5.
- **Explicitly NOT a risk, with reasoning:** no schema migration, no RLS policy change, no `lessons` row change, no enrollment change. None of these are touched by this plan.

### Failure hold — procedure if a policy defect is found after upload

**NEW, 2026-07-26, judge-remediation pass (J-019).** Applies if any authorization test fails at G13.8 or later, or if a defect is otherwise discovered after the real lesson-content artifacts have been uploaded to production.

1. STOP. Do not merge, do not deploy, do not publish, do not proceed to the deploy-safety plan's G9c.4 or G12.
2. Delete the 78 `lesson_content` storage objects and their 78 resource rows.
3. Restore the prior manifest to exactly 312 resource rows and 390 storage objects, either by re-running provisioning with the `lesson_content` entry removed from `resolveResourceNaming`, or by restoring from the G13.7 dump.
4. Re-run the deploy-safety plan's G9a at its ORIGINAL figures (312 tuples, 390 objects) to prove restoration, with a re-readable evidence file under `docs/cutover-evidence/`.
5. Treat it as an incident: record root cause and a corrected mechanism before any retry. This is explicitly NOT "the test failed, adjust and re-run."

**Honest limit, stated rather than implied as complete containment.** Per R-Q2 and R-Q3, content already retrieved by a client cannot be recalled, and a CDN-cached response can outlive its token's own expiry. This procedure limits future exposure; it does not undo exposure that already occurred. That asymmetry is precisely why G13.6a is sequenced to prove the policy shape before any real content is uploaded, rather than relying on this procedure as the primary safeguard.
