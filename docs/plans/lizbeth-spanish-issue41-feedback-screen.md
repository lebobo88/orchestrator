### Design brief

Audience: student users submitting free-text feedback/topic suggestions during lesson work; course owners/admins triaging that feedback in a master/detail inbox. Problem: `FeedbackForm.tsx`/`.css` and `OwnerFeedbackPage.tsx`/`.css` are hand-rolled and off-system — non-compliant character counter, single-signal (color-only) error treatment, a bespoke submit button instead of the shared `Control`, a bespoke custom-chevron select found nowhere else in the codebase, and an owner list that is a plain truncated-card list rather than any ledger/table structure with a bare-text empty state. Desired outcome: both screens read as native Field Journal surfaces — C.2-compliant fields/selects, a single primary submit, a two-signal terracotta-plus-mono error language, and a C.7-derived owner ledger with a C.9 empty state — using existing canonical, already-tested primitives wherever one exists, with new pieces introduced only where no primitive covers the need (selects; the owner ledger row). Success measures: this plan's acceptance criteria are met; zero native dialogs; WCAG 2.2 AA holds at both 1440 and 390; the long-standing Phase 3d failures, traced to exactly the bugs this migration fixes, become resolvable.

Creative thesis: migration precision over invention — reuse what's tested, derive honestly and disclose where no mock exists, extend the system's existing typographic/geometric grammar (mono labels, hairline-to-heavy rule weights, hard-edged ink shadows, dashed-rule empty states) rather than adding new visual vocabulary.

Anti-goals: no new color palette, no new shadow/elevation language, no icon library (the chevron is replaced with a plain mono glyph consistent with the system's existing `←`/`→` typographic-character convention), no fabricated "answered" status field/section, no second primary control per screen.

### Journeys (from the UX spec)

**J1 — student submits feedback, @1440.** Student opens the feedback screen while signed in and sees a card headed "Leave a note," with a Type select (default "General feedback"), a Course select, a Lesson select, an empty content textarea showing a live counter "0000 / 5000," and exactly one primary button, "Send the note." Course context loads in the background; until it resolves the Course select is disabled and the Lesson select stays disabled regardless. Once a Course is picked, Lesson enables and lists that course's unlocked lessons; both remain optional. The counter updates on every keystroke in zero-padded form (`0114 / 5000`); input is hard-capped at 5000 characters. Clicking "Send the note" with empty content moves focus to the textarea, turns its rule terracotta, and renders a mono error line beneath it; no submission occurs and the button never enters a busy state. A valid submit disables/busies the button, shows a polite "Submitting your feedback…" line, then on success clears the textarea and shows a polite confirmation line ("Thank you — your feedback has been submitted."). A submission failure shows an assertive error line in place of the confirmation, without clearing the student's typed content, and the student can retry. If course context fails to load, the Course select stays disabled and a polite inline line reads "Course context could not load." next to a "Try again" control that re-attempts the load in place with no page reload and no native dialog.

**J2 — student submits feedback, @390.** Identical to J1, except: the three selects stack in one column in the same order; the button label reads "Send note"; §E.5's mobile-only "Filed earlier" answered-history section is deliberately absent (disclosed deviation, decision D2).

**J3 — owner reviews feedback, @1440.** Owner opens the feedback inbox and sees a "Filter type" select above a ledger with a dark, mono-labeled header row (Student / Type / Context / Submitted / Excerpt) and a detail pane reading "Select a note to read the full submission." If no feedback exists yet, the ledger is replaced by a single C.9 empty-state panel — dashed rule, graph-paper ground, a spot illustration, and short body copy — never a bare "No feedback yet" text block. Clicking a row's student-name button gives that row a visible left-border accent, sets it as current (`aria-current="true"`), updates the URL, and loads the full detail (sender, timestamp, context, untruncated content) in the adjacent pane; the previous row's marker clears. Owner pages through further rows with Previous/Next. If the inbox fails to load, the ledger is replaced by an assertive error with a "Retry" control; if only a single detail fails, just the detail pane shows its own assertive error with a "Back to inbox" control, and the list stays intact.

**J4 — owner reviews feedback, @390.** The ledger collapses to one full-width, tappable card per submission, preserving the same data (student, type, submitted date/time, context, a two-line excerpt). Tapping a card selects it (same left-border and current-row marker) and navigates to a full-width detail view with its own "Back to inbox" control, replacing the list in view. Empty/error states reflow to single-column full width.

Owner inbox load error uses `role="alert"` (it blocks primary content). Detail-pane load error uses `role="alert"`, scoped to the detail region only.
