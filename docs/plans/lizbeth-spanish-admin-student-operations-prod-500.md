## What is actually established (repository and documentation evidence)

### The failing call path (client side)

`src/services/adminStudentData.ts`, function `registerStudent`, lines 54-75, calls:

```
client.functions.invoke('admin-student-operations', { method: 'POST', body: { action: 'register', payload: { email } } })
```

On any non-2xx response it executes, at line 67:

```
if (error) throw new AdminStudentError(`Failed to register student: ${error.message}`, undefined, error)
```

This never reads `error.context`, so the real server response body is discarded, and the operator sees only the generic string "Failed to register student: Edge Function returned a non-2xx status code." The `if (data?.error)` branch at line 70 is unreachable for a non-2xx response, because `data` is not populated on failure. This identical discard pattern repeats at lines 94, 118, 147, 182, 209, 237, 257, and 308 in the same file, and at line 142 of `src/services/ownerSettingsData.ts`. `getBands` (line 286) is a direct table read and is not affected by any of this.

Supabase's own documentation names the fix directly (https://supabase.com/docs/guides/functions/error-handling):

```
if (error instanceof FunctionsHttpError) {
  const errorMessage = await error.context.json();
}
```

This is corroborated by three open community issues against `supabase/functions-js` (#45, #51, #55) describing the same discard behavior as a recurring point of confusion.

### An out-of-directory import exists, but is unlikely to be this incident's cause

## Second amendment, 2026-08-04 — new evidence, repository investigation, and revised ranking

This amendment is triggered by two things happening together: the user checking the Dashboard Logs view and finding it empty, and a completed read-only repository investigation. Neither alone would have been decisive; read together, against the documentation cited below, they invert the original ranking.

### New evidence: empty Logs view, read correctly

**RE-11 — Supabase documents status codes by origin, and 500 is documented as function-generated, not gateway-generated.** The platform/gateway statuses issued before the worker runs are 401, 404, 405, and 503 (`BOOT_ERROR`). HTTP 500 is listed under "Function-Generated": "Your Edge Function threw an uncaught exception (`WORKER_ERROR`)." Source: https://supabase.com/docs/guides/functions/status-codes (accessed 2026-08-04). Consequence: the gateway does not emit 500 at all, so "the request was rejected at the gateway before reaching function code" cannot explain a 500. The original plan's framing of an empty log as evidence *for* a gateway rejection was incorrect and is marked superseded above.

**RE-12 — The dedicated 500 troubleshooting page gives an explicit decision rule that matches the observed evidence.** It states the cause is one of two things: "The function encountered an unhandled JavaScript error" or "Your code deliberately returned a 500 response." It instructs querying Log Explorer for status 500 with error-level logs, and states: "No results returned: indicates 'Your code deliberately returned a 500.'" Results returned indicates an unhandled JS error instead. Source: https://supabase.com/docs/guides/troubleshooting/edge-function-500-error-response (accessed 2026-08-04). Consequence: the user's observation of no log entry is, read against this documented rule, evidence *for* "the handler executed and deliberately returned a 500" and evidence *against* both the uncaught-exception hypothesis (H-A) and any gateway hypothesis.

**RE-13 — the Logs view and the Invocations view are different views, and this distinction is now decisive.** Logs shows "platform events, uncaught exceptions, and custom log messages." Invocations shows "request/response data including headers, body, status codes." A deliberate `return new Response(..., {status:500})` produces no Logs entry but does appear in Invocations with status 500. Source: https://supabase.com/docs/guides/functions/logging. Consequence: if the user checked only the Logs view, its absence proves nothing on its own about whether the function ran. Checking the Invocations view, filtered to status 500, is the single decisive, zero-risk next action, and it is elevated to the top of the revised Phase A below.

**RE-14 — the log retention window and any ingestion delay are not stated in the official logging or log-drains documentation.** If the failed request is older than retention, an absence from Logs is uninformative either way. Recorded as an open unknown.

**RF-11 — there is exactly one deliberate-500 site reachable by `action: 'register'`, and it is the prime suspect.** `supabase/functions/admin-student-operations/index.ts` lines 187-189:


## Reviewed error-state design

This design was reviewed by an independent design reviewer across two rounds. The first round returned NEEDS_REVISION on three findings, all corrected in the version below: the redaction rule originally over-redacted UUIDs (a 36-character UUID matched the generic 32-plus-character rule, which would have stripped the "which record failed" detail the design exists to preserve); the focus fix was originally specified as a `.focus()` call inside the catch block, which silently does nothing because the target input is still `disabled` at that point in the render cycle; and an entire realistic error class, not-found (404), was missing from the original evidence read. The second round verified all cited line numbers, the 404 line numbers, the `.detail-save-error` orphan claim, the uncaught `onReenable` gap, the CSS-token claims, the preserved-selector list, and Browser UI invariant conformance, and passed the design.

**Direction: reuse the existing system entirely.** No new component, no visual refresh, no new design tokens. Reuse `.form-error`, `.admin-students-error`, the currently orphaned `.detail-save-error`, `.demo-button.secondary.small`, `.detail-back-link`, and the existing `role="alert"` / `role="status"` conventions.

**Three presentation tiers**, chosen by where the failing action lives, not by error class:

1. Field-level, under the input — used only for a 422 response naming a specific field (register's email is the only reachable case today).
2. Form or section-level banner — `.form-error` inside a modal, or `.detail-save-error` / the assign-error `.form-error` on the detail page. This is the default tier for every other operation failure.
3. Page-level `.admin-students-error` — reserved for roster or detail *load* failures only. There is no fourth surface, and no toast.

**Copy template**, shared by five of the six classes: `Couldn't {actionPhrase}. {detail}` — if `detail` is empty: `Couldn't {actionPhrase}. The server didn't provide more detail.` Engineering appends a period if `detail` lacks terminal punctuation.

`actionPhrase` by operation: register -> "create the account"; disable -> "disable this account"; enable/re-enable -> "re-enable this account"; delete -> "delete this account"; assign / reassign / assign-new-band -> "assign this band"; unassign -> "unassign this band"; wipe-save -> "wipe this save"; roster load -> "load the student list"; student detail load -> "load this student's details".

**Class A — field-level validation (422 with `fieldErrors`).** A new `<p id="{field}-error" className="form-error">` directly below the input, replacing the generic banner for that submission. Copy is the server's `fieldErrors[0].message` verbatim, with fallback "Enter a valid email address." No Copy-details control. The input gets `aria-invalid="true"` and `aria-describedby="{field}-error"` while the error is shown, cleared on the next change or submit. This is not a live region.

**Class B — conflict / expected operational failure (500 with a known-condition message).** Existing `.form-error` slot. Illustrative copy: "Couldn't create the account. A user with this email has already been registered." (Illustrative — engineering substitutes the real server text once C1 recovers it.) The modal stays open, the submit control is re-enabled, and focus returns to the field.

**Class C — authorization (401/403).** Same slot. Copy: "Couldn't {actionPhrase}: you don't have permission to do this, or your session has expired. Sign out and sign back in, then try again." No Copy-details. No new sign-out control is introduced.

**Class D — server/config (500, unclassified). This is the class that must be reportable, and is the direct answer to this incident's operator-visibility problem.** Same slot, plus an expandable detail block and a "Copy details" button. Copy: `Couldn't {actionPhrase}. The server reported: "{detail}".` The redacted string is truncated at 160 characters plus an ellipsis, with a `.detail-back-link`-styled "Show full message" / "Show less" toggle that reveals a `<pre>`-style block reusing `.temp-password-display code`'s monospace treatment, capped at a maximum height with vertical scroll. "Copy details" uses `className="demo-button secondary small"` and copies the full, untruncated, redacted string via `navigator.clipboard.writeText`. Confirmation reuses `.temp-password-copied-message`, with `role="status" aria-live="polite"` and text "✓ Copied to clipboard".

**Class E — network/offline.** Same slot. Copy: "Couldn't {actionPhrase}: the app couldn't reach the server. Check your connection and try again." No Copy-details.

**Class F — not-found (404).** The Edge Function returns real 404s at index.ts lines 220, 248, 283, 337, 343, 361, 413, 449, and 540 (disable, enable, delete, three assign variants, unassign, wipe-save, and student-detail). This is reachable whenever a stale view has been changed in another session. Register cannot 404, because no lookup precedes user creation. Placement follows the same slot rule as classes B/D, per operation. Copy: "Couldn't {actionPhrase}. {server text}. The record may have changed in another session — try Refresh." (See C3 for the required rewording of this copy on the student detail page, where no Refresh control exists.) No Copy-details.

**Accessibility (binding).** Preserve `role="alert"` on every existing banner (`RegisterStudentModal.tsx` line 115, `AdminStudentModals.tsx` line 55, `AdminStudentsPage.tsx` line 173); do not add a competing live region. The field-level error (class A) is explicitly not a live region.

Focus management is a real, currently verified defect, not a hypothetical one: `#student-email` is `disabled={isLoading}` (line 109) and the submit button is `disabled={isLoading || !email.trim()}` (line 129), so after a failed submit today, focus lands on `<body>`. The required fix is:

```
useEffect(() => { if (error) targetRef.current?.focus(); }, [error]);
```

Not a `.focus()` call inside the catch block — at catch time, `isLoading` is still `true` in the last-committed render, the node is still `disabled`, and the call silently does nothing. This mechanism is reliable even on a repeated identical failure, because every catch-handling component already calls `setError(null)` synchronously at the start of each attempt (`RegisterStudentModal.tsx` lines 52-63; `AdminStudentModals.tsx`'s `DisableStudentModal` lines 33-44, `HardDeleteStudentModal` lines 122-134, `UnassignModal` lines 228-239, `ReassignModal` lines 291-304, `WipeSaveModal` lines 393-405), so the error state genuinely transitions string -> null -> string on every attempt. Apply the effect to `RegisterStudentModal`'s email input, `HardDeleteStudentModal`'s and `WipeSaveModal`'s confirmation text inputs (lines 167-175 and 435-443), and to the confirm button in `DisableStudentModal`, `UnassignModal`, and `ReassignModal`, none of which have a text input to focus instead.

Non-color-dependent indication is already satisfied by the existing text-plus-left-border pattern. The contrast gate is the existing `src/__tests__/designSystemConsistency.test.ts` line 125.

**Redaction rule.** Restated from C2 above: only the parsed body's plain `error` string and `fieldErrors[].message` strings may ever render. Never render `error.stack`, never the raw `context` or `Response` object, never any request-payload field, and never let a temporary password reach an error string. The five-step ordering (UUID allowlist first, then JWT redaction, then generic high-entropy redaction, then truncation, then and only then render/clipboard) is a hard security constraint, not a style preference — see Risks below for why the ordering matters.

**Selectors that must keep resolving**, enforced by `src/__tests__/e2e/gap-4-admin-students-remediation.spec.ts`: `.modal-title`, `#student-email`, the "Add Student" / "Create Account" / "Disable" / "Re-enable" buttons, `.temp-password-display code`, `.temp-password-copied-message`, `[role="dialog"]`, `.roster-item`, `.roster-item-email`, `.roster-item-band`, `.status-badge`, `.status-active`, `.status-pending_first_login`, `.detail-status .status-badge`, `.detail-assign-new-band` and its `select` / "Assign" button, `.enrollment-item`. Also preserved, though not directly enforced by that spec: the "Cancel" / "Done" / "Copy" buttons.

**Browser UI invariant.** Conformant as designed. Zero native browser dialogs are introduced; all content renders inside the existing app-owned `Modal` component or the existing page tree. The repository already gates this globally via `src/__tests__/nativeDialogPolicy.test.ts`.

**Known caveat, flagged but not fixed by this plan.** `--color-ink-800` and `--color-ink-900` are genuinely defined in `:root` (`App.css` lines 22-23, `#3d3530` / `#2a2420`), but `--color-error-50/600` and `--color-warning-50/600` are never defined in `:root` anywhere in the repository — every usage is a bare `var(--token, #fallback)`, and the fallback for the same nominal token already disagrees between files (`--color-warning-600` is `#d97706` at `AdminStudentsPage.css` line 104, versus `#f59e0b` at `RegisterStudentModal.css` line 118). This is pre-existing and out of scope for this plan. Any new usage introduced by C3 must copy whichever fallback already exists in the file being edited, rather than widening the inconsistency.
