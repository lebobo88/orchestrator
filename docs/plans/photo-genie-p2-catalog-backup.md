## 4. Scope and non-goals

### 4.1 In scope — the seven directed capabilities

1. **Core backup primitive over the catalog** (`photo-genie.pgcat`). Backs up catalog content only: recipes (`images.recipe_json`), append-only `edit_history`, `snapshots`, `presets`, `collections` + `collection_images`, `keywords` + `image_keywords`, IPTC fields (`images.title`/`caption`/`copyright`/`creator`), and all other catalog tables. **Excludes** original/RAW files (assumed to exist elsewhere on the user's filesystem) and the regenerable `.pgcache` thumbnail cache.
2. **Restore** — provable end to end, not merely "backup is valid SQLite."
3. **In-app scheduler** (NOT an OS daemon/tray service): interval Never/Every-close/Daily/Weekly/Monthly evaluated at launch plus a required in-app timer plus an on-exit fallback prompt, against a persisted last-successful-backup timestamp.
4. **User-configurable backup location** with a sensible default and an override via the OS-native folder picker.
5. **Non-local/removable/network destination detection** with a fail-closed default policy.
6. **Automatic pre-migration/pre-version-upgrade backup** plus a **transactional migration safety fix** plus a **version-too-new fail-closed gate**.
7. **Failure-path integrity**: `PRAGMA integrity_check` on every backup copy; a hard-to-miss critical alert on failure; the last-successful-backup timestamp advances **ONLY** on verified success, across all three trigger paths.

## 6. Research evidence and disposition

Research was performed by a nested Researcher and is authoritative for the questions below; each is cited as delivered.

- **Q1 — Lightroom Classic backup behavior** (Adobe helpx back-catalog documentation; Lightroom Queen): Lightroom's "Back Up Catalog" is an **on-exit prompted dialog**, not a background timer, with a fixed frequency dropdown (Never / Once a month/week/day when exiting / Every time it exits / When it next exits), plus "Test integrity before backing up" and "Optimize catalog after backing up" checkboxes, writing a ZIP to a timestamped subfolder under a default Backups folder next to the catalog. **Disposition:** the P2 interval model (launch evaluation plus a required in-app timer plus an on-exit fallback, evaluated against a persisted last-successful-backup timestamp) is a faithful, safer superset of Lightroom's model — it also covers the crash/not-clean-exit case Lightroom misses, and (per Remediation, Section 8) makes the timer a required rather than optional trigger path. This is a grounded interpretation, stated plainly rather than presented as a literal Lightroom feature match.
- **Q2 — SQLite safe hot-backup under WAL** (SQLite official `lang_vacuum`, `backup`, `wal`, `pragma` documentation; SQLite forum): both `VACUUM INTO 'file'` and the Online Backup API (`rusqlite Connection::backup`) operate through the live connection and capture all committed data, including committed frames still in the WAL, with no manual checkpoint needed, producing a standalone single-file copy needing no `-wal`/`-shm` sidecar. `VACUUM INTO` additionally defragments (doubling as Lightroom's "optimize") and is read-only on the source, but **cannot** run inside an explicit transaction and requires no open transaction and no unfinalized prepared statements at call time. A raw OS file copy of an open WAL-mode `.pgcat` is **unsafe**. **Recommendation adopted:** use `VACUUM INTO` as the primary primitive (run via `with_conn` holding the single `Mutex<Connection>` as sole accessor; ensure no open transaction), with `Connection::backup` as the ready fallback. Gate every backup with `PRAGMA integrity_check` (or the faster `quick_check`) on the resulting copy before promoting it to last-known-good; a failure on a copy of a supposedly-clean source implies the source is already corrupt. Restore-by-file-replacement is sound only if sidecars are handled: snapshot the current catalog first, close/checkpoint the live connection, replace the live `.pgcat` with the standalone copy, delete any stale `-wal`/`-shm` belonging to the old catalog (must not be replayed onto the new file), reopen, run `integrity_check` on the restored DB, and never delete the prior good backup until the restored catalog verifies.
- **Q3 — destination detection and atomic rename** (Microsoft Learn `MoveFileEx`/`GetDriveTypeW`; LWN; the `windows` crate): write each backup under a new timestamped filename to a temp file in the **same directory** as the destination, then rename — a non-superseding same-directory rename is atomic on NTFS and POSIX, sidestepping the Windows large-target superseding-rename caveat. Atomic rename does **not** hold on FAT/exFAT, network shares (SMB), or removable media that can vanish mid-operation. Detect the destination via Win32 `GetDriveTypeW` (`DRIVE_FIXED`/`REMOVABLE`/`REMOTE`/`CDROM`/`NO_ROOT_DIR`/`UNKNOWN`) plus a UNC-prefix check (UNC returns `NO_ROOT_DIR`) plus `GetVolumeInformationW` for filesystem name (NTFS versus FAT/exFAT). Minimal new dependency: the official `windows` crate with the `Win32_Storage_FileSystem` feature (Windows-only, no runtime dependencies). **Recommended policy adopted (fail-closed default, justified by data safety):** `DRIVE_FIXED`+NTFS → proceed; `DRIVE_FIXED`+FAT/exFAT → warn plus fsync plus `integrity_check` plus keep the prior good backup; `REMOVABLE`/`REMOTE`/`CDROM`/UNC/`UNKNOWN` → fail-closed for the authoritative backup by default, offering stage-locally-then-copy-as-secondary with an explicit accepted-risk acknowledgement. Never let the only backup live on a non-atomic/removable/network target; never overwrite last-known-good until the new copy passes `integrity_check`.
- **Q4 — PRD requirement quotes** (`docs/specs/PRD.md`): **LIB-04** (line 50): "The system MUST provide catalog backup and an integrity/optimize check, and MUST be able to recover from or report catalog corruption." (P0). **NFR-SAFE-02** (line 266): "The catalog MUST support scheduled/on-exit backup and integrity check (backs LIB-04)." Adjacent: **Acceptance 4.1** (line 289): "Trigger catalog backup; a backup artifact is produced and an integrity check reports OK." **NFR-SAFE-03** (line 267): "A crash or restart MUST NOT lose committed edits."
- **Q5 — Durability sequencing for the standard fixed-NTFS path** (added in this revision to remediate `PLAN_DUCK` finding J-P2-DURABILITY-GAP, Section 8): nested Researcher evidence — Rust `std::fs::File::sync_all`/`sync_data` documentation; Microsoft Learn `FlushFileBuffers` and `MoveFileExW`/`MOVEFILE_WRITE_THROUGH`; SQLite Atomic Commit documentation; Dan Luu, "Files are hard"; Evan Jones on durability; Pillai et al., OSDI'14 crash-consistency study; BonsaiDb durable-writes documentation. **Findings:** on Windows, `File::sync_all()` maps to `FlushFileBuffers` and flushes both file data and metadata; `sync_data()` collapses to the same call on Windows but does not guarantee metadata on other platforms, so `sync_all` is the correct, portable choice. `std::fs::rename` does **not** itself flush the rename's directory-metadata change; Windows exposes no clean portable directory-fsync equivalent to POSIX's fsync-the-parent-directory pattern, and a volume-handle `FlushFileBuffers` call requires administrator privilege and flushes the whole volume, making it unsuitable here. `MoveFileExW` with `MOVEFILE_WRITE_THROUGH` offers a best-effort same-volume metadata flush on rename as optional additional hardening. SQLite's own atomic-commit design and the crash-consistency literature (Pillai et al.) confirm that data-durability-before-rename, plus an integrity check on the durable copy before promotion, is the standard pattern for avoiding torn or partially-written artifacts. **Disposition:** this evidence is adopted verbatim into Track A1's durability sequence (Section 9.1) per Remediation 1 of the `PLAN_DUCK` disposition (Section 8).

- **Q6 — Default backup-location resolution and OneDrive Known Folder Move interaction** (added in this revision to ground Decision 3, Section 14.3; nested Researcher evidence, authoritative): Microsoft Learn `SHGetKnownFolderPath`; Microsoft Learn `KNOWN_FOLDER_FLAG` enumeration; `windows-docs-rs` (docs.rs) documentation for `SHGetKnownFolderPath` and `FOLDERID_Documents` (`Win32::UI::Shell`); Microsoft/OneDrive documentation on Known Folder Move (KFM); Microsoft Learn File Attribute Constants (`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`, `FILE_ATTRIBUTE_OFFLINE`, `FILE_ATTRIBUTE_REPARSE_POINT`, `FILE_ATTRIBUTE_PINNED`). **Findings:** `SHGetKnownFolderPath(FOLDERID_Documents, dwFlags, hToken, &path)` resolves the current Documents location; `dwFlags=0` (`KF_FLAG_DEFAULT`, distinct from `KF_FLAG_DEFAULT_PATH`) returns the CURRENT/redirected path rather than the original default — the correct choice when OneDrive KFM is active. The caller must free the returned `PWSTR` via `CoTaskMemFree`; the returned path has no trailing backslash and the folder itself may not exist and must be created (`std::fs::create_dir_all`). When OneDrive KFM is active — a mainstream, expected configuration on both managed and consumer Windows machines — `FOLDERID_Documents` resolves under the local OneDrive sync root (e.g. `%USERPROFILE%\OneDrive\Documents`); this is still a local, fixed, NTFS directory (`GetDriveTypeW` returns `DRIVE_FIXED`, the path is non-UNC, `GetVolumeInformationW` reports NTFS), so the finalized fail-closed destination policy (Q3 above; Track C1) is unaffected and correctly proceeds. OneDrive may later dehydrate a backup file to a cloud-only placeholder, marked via `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`/`OFFLINE`/`REPARSE_POINT` and detectable via `GetFileAttributesW`; a dehydrated file transparently rehydrates on read while online but fails to read while offline. `FILE_ATTRIBUTE_PINNED` can be set to keep a file permanently hydrated locally. **Disposition:** adopted verbatim into the Decision 3 resolution (Section 9.4, Track D1): the (possibly OneDrive-redirected) Documents folder is accepted as the default AS-IS, with a non-blocking informational note for cloud-synced locations and an optional `FILE_ATTRIBUTE_PINNED` hardening elective. This is a correctness-preserving, availability-only consideration; it does not reopen the fail-closed policy.

**Researcher-flagged residuals:**

1. (moderate confidence) the exact `std::fs::rename` Windows syscall mapping is toolchain-version-dependent. If strict atomicity is load-bearing, verify against the target toolchain or use an explicit `MoveFileExW`/rename call. This is folded into acceptance as a verification step (Section 11).
2. (documented accepted limit, Q5) `MOVEFILE_WRITE_THROUGH`'s same-volume metadata-flush guarantee is **best-effort**: Microsoft's own documentation centers its stated guarantee on copy/delete operations rather than same-volume rename, so it should be treated as hardening, not a proof. Physical durability of any `FlushFileBuffers`-backed call ultimately depends on the physical drive honoring the flush request — drive write-caching or registry policy can defeat it on some systems. Both limits are documented in Section 9.1 as accepted risk, not engineered around, because no portable software-only mechanism closes them.

## 9. Ordered work

### 9.1 Track A — Core backup primitive and integrity (foundational; blocks the rest)

- **A1.** Implement a Rust backup function with the following platform-appropriate durability sequence for the standard fixed-NTFS path (adopted from Section 6, Q5, remediating `PLAN_DUCK` finding J-P2-DURABILITY-GAP):

  1. `VACUUM INTO` a temp file in the **same directory** as the destination.
  2. `File::sync_all()` on the temp file — this maps to `FlushFileBuffers` and makes the file's data **and** metadata durable. Use `sync_all`, **not** `sync_data`: on Windows `sync_data` collapses to the same call, but `sync_all` is the one that guarantees metadata durability, including on other platforms. (One-line implementation check: confirm `VACUUM INTO`'s own fsync behavior does not obviate this step — step 2 makes the question moot regardless, because it is performed unconditionally.)
  3. `PRAGMA integrity_check` (or `quick_check`) against the temp file; on failure, do **NOT** delete the temp file. Abort the promotion path and instead rename/move the temp file to a clearly non-promoted, clearly-marked failure filename in the destination directory (e.g. `photo-genie-backup-YYYY-MM-DD_HHMMSS.failed`, or an equivalent `-failed`/timestamped-failure suffix distinct from the normal backup naming used in step 4), so the quarantined artifact can never be confused with a valid promoted backup. Surface the failure via S3 (Section 7.1), referencing the quarantined file's path via Show Backup File Location. The last-successful-backup timestamp is never advanced on this path (also stated in step 6 and Acceptance (d) below).
  4. Atomic non-superseding rename of the temp file to a **new timestamped final filename** (e.g. `photo-genie-backup-YYYY-MM-DD_HHMMSS.pgcat`) in the destination directory.
  5. Rename-durability handling: **DEFAULT** — accept NTFS metadata-journal ordering as a documented accepted-risk bound (see below); Windows exposes no clean portable directory-fsync, `std::fs::rename` does not itself flush the rename's metadata, and a volume-handle `FlushFileBuffers` call is inappropriate (admin-only, whole-volume). **OPTIONAL hardening engineering may elect:** perform the rename via a `windows`/`winapi`-crate `MoveFileEx(..., MOVEFILE_WRITE_THROUGH)` call for a best-effort metadata flush on rename (this remains a non-blocking engineering elective, not forced — see Section 14.4).
  6. **Only after** the rename returns success, persist/advance the last-successful-backup timestamp, via its own atomic-durable config write (Section 9.4, Track D1). The order is strict: flush temp (`sync_all`) → integrity check → rename → optional best-effort rename-durability hardening → persist timestamp. The timestamp is never persisted before the file bytes are durable.

  **Failure-artifact retention:** a quarantined failure artifact produced by step 3 is not automatically deleted at any later point either. It persists until the user manually removes it (e.g., via Show Backup File Location, S3) or otherwise clears the destination directory. This plan does not define an automatic age- or count-based cleanup policy for these artifacts — consistent with the fact that no retention/pruning policy exists elsewhere in this plan for successful backups either. Automatic cleanup of quarantined failure artifacts is therefore a small, undecided scope item outside this correction; implementation must not invent silent auto-deletion in its absence.

  **POSIX portability note** (documented, not implemented on this Windows-hosted phase): on Linux/macOS, additionally fsync the parent directory between the rename and the timestamp persist; this is a POSIX concept with no clean Windows equivalent.

  **Accepted-risk bound (state plainly):** because the bytes are `FlushFileBuffers`'d before the rename, a power loss after "success" can never leave a torn, truncated, or corrupt backup, and can never corrupt the filesystem. The only residual risk is loss of the newest directory-entry change (the timestamped rename) in a sub-second pre-commit window — in which case either the backup survives under its temp name, or the directory reverts to the prior consistent state with the previous backup intact. **Mitigation:** the persisted last-successful-backup timestamp is treated as advisory — on load, verify the referenced newest backup file actually exists; if missing, scan the backup directory for the newest valid backup and reconcile the timestamp (self-correcting). Also documented, not engineered around: `FlushFileBuffers` can be defeated by drive write-cache or registry policy on some systems, which is an inherent hardware/OS limit (Section 6, Q5, residual 2).

  Expose as a Tauri command (plus a devbridge route) following the thin-wrapper pattern.

  **Acceptance:**
  - (a) a committed-but-uncheckpointed WAL row is present in the backup copy;
  - (b) the copy is a standalone valid SQLite file needing no sidecar;
  - (c) an injected mid-write failure never promotes a partial final file;
  - (d) an injected integrity failure does NOT advance the last-successful-backup timestamp and preserves the artifact;
  - (e) **fault-injection validation** (new, remediating J-P2-DURABILITY-GAP): simulate a crash/kill at points between step 2 (`sync_all`) and step 6 (timestamp persist) — specifically both **after the integrity check** and **after the rename** — and assert on restart that: no zero-byte/torn backup is ever loaded; either the newest backup or a valid prior backup restores cleanly; and the timestamp reconciles via the directory-rescan mitigation above. Assert the timestamp is written strictly after the rename returns in every injected scenario.
- **A2.** Backup content scope: verify the copy contains recipes, `edit_history`, `snapshots`, `presets`, `collections`+members, `keywords`+mappings, IPTC — and excludes `.pgcache` (regenerable) and original/RAW files.
  **Acceptance:** the restore proof (B1) asserts distinctive representative content in each of these tables survives.

### 9.4 Track D — Configuration and scheduler

- **D1.** Persist backup settings (location, interval) and the last-successful-backup timestamp in a net-new app-config store **outside** the catalog (recommended: a JSON file under Tauri `app_config_dir` via `tauri::Manager` `path()`, so config plus real backup history survive a catalog restore/corruption). Capture `AppHandle` in setup (currently discarded at `lib.rs:984`). Scope the scheduler/config/picker to the Tauri runtime; the core backup command remains testable via devbridge/unit tests.

  **Default backup location (Decision 3, Section 14.3; finalized 2026-07-17):** resolve the OS default via `SHGetKnownFolderPath(FOLDERID_Documents, dwFlags=0, hToken=NULL)` from the `windows` crate (`Win32::UI::Shell`). Use `dwFlags=0` (`KF_FLAG_DEFAULT`), **not** `KF_FLAG_DEFAULT_PATH`, so the CURRENT/redirected location is returned. Then create a dedicated subfolder under it (working name "PhotoGenie Backups"; engineering may align the exact name to any existing app naming precedent — none exists in this repository today, so the exact name is a non-blocking engineering elective, Section 14.4) via `std::fs::create_dir_all` before the first write, since the resolved Documents path may exist while the subfolder does not. Free the returned `PWSTR` with `CoTaskMemFree`; the returned path has no trailing backslash.

  **OneDrive Known Folder Move (KFM) interaction (grounded, Section 6 Q6; does not reopen the fail-closed policy):** when OneDrive KFM is active — a mainstream, expected case on managed and consumer Windows — `FOLDERID_Documents` resolves under the local OneDrive sync root (e.g. `%USERPROFILE%\OneDrive\Documents`). That redirected path remains a LOCAL, fixed, NTFS directory: `GetDriveTypeW` returns `DRIVE_FIXED`, the path is non-UNC, and `GetVolumeInformationW` reports NTFS. The finalized fail-closed destination policy (Track C1, Section 9.3) therefore correctly PROCEEDS on a KFM-redirected default, and same-directory atomic rename (Track A1) still holds. OneDrive redirection introduces no case the drive-type detection mis-handles, and it does not reopen the fail-closed policy.

  **Residual consideration — availability, not corruption:** a freshly written backup is durable on local disk immediately; the local `sync_all` → integrity-check → rename sequence (Track A1) completes locally and does not wait on OneDrive's asynchronous cloud upload. A backup later dehydrated by OneDrive to a cloud-only placeholder (`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`/`OFFLINE`/`REPARSE_POINT`) transparently rehydrates on read while online, but reading a dehydrated only-copy while OFFLINE fails. This is a disaster-recovery/availability consideration, not a correctness or corruption risk, and is documented as an accepted characteristic of the default location rather than engineered around.

  **RESOLUTION (decided design judgment, Decision 3):** accept the (possibly OneDrive-redirected) Documents folder as the default AS-IS — local, fixed, NTFS, atomic-rename-safe, with free offsite redundancy as a bonus. ADD a light, non-blocking, app-owned informational note (never a native dialog, per the Browser UI invariant) surfaced in S1 (and S6 where relevant, Track F) when the resolved default or a user-chosen location is detected under a OneDrive/cloud-synced prefix. Detection: OneDrive path-prefix match, the `OneDrive`/`OneDriveConsumer`/`OneDriveCommercial` environment variable, or the `RECALL_ON_DATA_ACCESS`/`OFFLINE`/`REPARSE_POINT` attributes via `GetFileAttributesW`. The note covers (i) privacy — backup copies are uploaded to the cloud — and (ii) restore availability — a cloud-only backup may need re-download and requires network access at restore time. Cloud-synced destinations are **NOT** fail-closed: a synced local NTFS folder is genuinely atomic, and fail-closing it would contradict the finalized "fail-closed only for genuinely non-atomic destinations" policy (Decision 4) and would break the mainstream default. **Optional engineering hardening (recommended, not forced; non-blocking elective, Section 14.4):** set `FILE_ATTRIBUTE_PINNED` on the backup folder to keep backups fully present locally and guarantee offline restore.

  **Backup-location resolution precedence** (new, remediating `PLAN_DUCK` finding J-P2-PREMIGRATION-LOCATION-AMBIGUITY): used uniformly by **all three** triggers — manual (A1/S1), scheduled (D2), and pre-migration (E1):
  1. Load the persisted override from the app-config: parse **then** validate; a corrupt/partial config from an interrupted settings update is treated as "no valid override," never a crash.
  2. If a persisted override is present, and its path exists/is reachable, and it passes the destination policy (Track C1), use it.
  3. Else, if no override is present, use the default location (if the default itself is valid).
  4. If the chosen location fails the destination policy or is unreachable: for the **pre-migration case specifically**, fail closed — block the migration (S4 backup-failed) with a clear message (e.g. "Your configured backup location is unreachable or unsafe; fix it before upgrading"); do **not** silently fall back to a different location, and do **not** proceed with the migration. This resolution must happen and be validated **before** the migration transaction begins (see Section 9.5, E1).

  **Mandatory per-write destination re-classification (binding requirement, added 2026-07-18 remediating finding J-P2-DESTINATION-JOB3-ENFORCEMENT-GAP; see Section 8.2):** the destination-classification function (`classify_destination`, introduced by Track C1's destination-detection work, Section 9.3) MUST be invoked immediately before **every individual backup write**, on **all three** trigger paths — manual (A1/S1), scheduled (D2), and pre-migration (E1) — not only during location resolution as described above. This classification result MUST NOT be cached, memoized, or reused: not across a scheduled interval, not across different trigger paths, and not from an earlier settings-load-time or app-startup-time check. Each write gets its own fresh `classify_destination` call, made as close as practically achievable to the point the write actually begins, so a destination that has been remapped, disconnected, or reassigned to network/removable storage since an earlier check is caught before that write, not merely before some earlier check. **Accepted residual risk (stated plainly, consistent with the Section 9.1 rename-durability accepted-risk framing):** an immediate-before-write check still leaves an unavoidable sub-second window between the `classify_destination` call and the write itself; a drive being remapped or disconnected within that specific window is an ACCEPTED RESIDUAL RISK, not eliminated by this requirement. This requirement bounds and minimizes that window by making re-classification immediate and mandatory before every write; it does not and cannot close it to zero. This is a binding requirement for Job 3's implementation of every write path that consumes Track C1's destination classification.

  The config **write** itself must be atomic-durable (temp file + `File::sync_all` + atomic rename, per the Track A1 sequence in Section 9.1), so an interrupted settings update can never yield a corrupt config. Load-time behavior is always parse-then-validate with fallback-to-default (or fail-closed if the default is itself invalid) — never a crash.

  **Acceptance:** settings round-trip and survive a simulated catalog restore; timestamp semantics documented; (a) a persisted override is correctly used for the pre-migration backup; (b) an interrupted-settings-update edge (half-written/corrupt config) is detected on load and treated as "no valid override" (falls to default, or fail-closed if the default is invalid) without crashing; (c) **KFM/OneDrive validation** (Decision 3, new): on a KFM-active machine, confirm the resolved default path is `DRIVE_FIXED`/non-UNC/NTFS and a full backup succeeds; force-dehydrate a backup and confirm an online restore transparently rehydrates and `integrity_check` passes, while an offline read of a dehydrated only-copy fails as expected (documents the availability gap, not a corruption risk).
- **D2.** Scheduler: **all three trigger paths are required, finalized as the design (not an option)** (remediating `PLAN_DUCK` finding J-P2-SCHEDULER-OPTIONAL — the timer is no longer optional):
  - Launch: evaluate the interval (Never/Every-close/Daily/Weekly/Monthly) at launch against the persisted last-successful-backup timestamp.
  - In-app timer (required): the app re-evaluates backup due-ness on a fixed cadence (recommended default: every 15 minutes) against the persisted last-successful-backup timestamp, so an app left open across a Daily/Weekly/Monthly boundary still triggers a backup at/after the boundary rather than only at the next launch.
  - On-exit fallback prompt (S5) when a backup is due.

  **Concurrency behavior:** a single in-flight-backup guard (an explicit "a backup is currently running" flag). A due-check (from timer, launch, or on-exit) that fires while a backup is already running is a no-op (coalesced) — it never starts a concurrent or queued second backup. The single `Mutex<Connection>` plus `VACUUM INTO` already serialize DB access; the guard additionally prevents redundant scheduling, and is the shared mechanism implementing the **finalized** S1-vs-S5 Coalesce decision (Decision 6, Section 14.3) — Coalesce is the decided design, not one of several options.

  **Acceptance:** deterministic tests that each interval correctly decides due/not-due against a fixed last-backup timestamp; a due backup at launch triggers A1; the last-successful-backup timestamp advances only on verified success (shared assertion with A1/E1); and, new for the **timer path specifically**: with a fixed/injected clock, an app that stays open across an interval boundary triggers exactly one backup at the boundary; a due-check that fires while a backup is running coalesces (no second backup starts); after a successful timer-triggered backup, the last-successful-backup timestamp advances and the next boundary is recomputed. The existing launch-path and last-timestamp-only-advances-on-verified-success tests remain.

### 12.3 Window-close-race executable procedure (Tauri runtime)

Added to remediate `PLAN_DUCK` finding J-P2-CLOSE-RACE-NONEXECUTABLE (Section 8): a concrete, step-by-step Tauri-runtime harness a Browser/Tauri validator can actually follow, replacing the prior "specify a procedure" instruction.

- **Preconditions:** seed a real catalog per `test-assets/SEED-PROCEDURE.md` so a real `photo-genie.pgcat` exists. Launch the Tauri runtime with `npm run tauri dev` (run from `photo-genie/`).
- **Deterministic in-flight seam:** a test-only injectable delay — a debug env var `PG_BACKUP_TEST_DELAY_MS`, read by the backup command, that inserts a sleep **after** `VACUUM INTO` + `File::sync_all` but **before** the atomic rename, so the backup is provably in-flight and not yet promoted. This seam must be compiled only in debug/test builds, or otherwise gated so it can never ship in release. Set it to 15000 (15s) for the run: launch with `PG_BACKUP_TEST_DELAY_MS=15000`.
- **Steps:**
  1. With the delay set, trigger a manual backup (S1 "Back Up Now").
  2. Within the 15s window, request an OS window close (click the window close button).
  3. Observe the `CloseRequested` handler call `api.prevent_close()` and show the app-owned S5 "backup in progress" state/modal instead of closing — this is the **first, prevented** close.
  4. Let the backup finish (delay elapses, rename completes, integrity OK, timestamp advances).
  5. Request close again — the **eventual, approved** close; the window closes cleanly.
- **Distinguishing first-prevented from eventual-approved:** instrument the `CloseRequested` handler to log/emit a distinct signal on each invocation (e.g. "close prevented: backup in flight" vs. "close approved: no backup in flight"), observed in the Tauri dev console/devtools.
- **Assertions:** exactly one new timestamped backup file exists and passes `PRAGMA integrity_check`; no partial/temp artifact was promoted to a final name; the last-successful-backup timestamp advanced exactly once and only after the rename; reopening the catalog passes `integrity_check` (no state corruption).
- **Skip/close-anyway variant:** if the user chooses Skip/close-anyway (S5 failure fork) while a backup is in flight, assert the in-flight backup either completes durably in the background, or is abandoned without promoting a partial artifact and without advancing the timestamp — never a silent partial success.
- **Cleanup/relaunch:** stop the Tauri runtime, run `seed-catalog --clean`, re-seed for the next journey; note the env seam is dev/test-only and must never ship in a release build.

## 13. Risks and rollback

**High risk.** Automatic/background-triggered behavior, arbitrary user-chosen write locations, and a backup step gating the migration/startup path all carry real data-safety consequences.

**Mitigations:** data-safety-first design (`VACUUM INTO` plus `File::sync_all` durability plus an integrity gate plus timestamped non-superseding rename plus a fail-closed destination policy plus a documented accepted-risk bound on rename-metadata ordering plus snapshot-before-restore plus never-delete-prior-good-until-verified plus timestamp-advances-only-on-verified-success, per Section 9.1); transactional migration; version-too-new fail-closed; a uniform fail-closed backup-location resolution precedence for pre-migration backups (Section 9.4-9.5); a required (not optional) in-app timer plus a single in-flight-backup concurrency guard (Section 9.4, D2); every failure surfaced honestly via an app-owned surface, never a silent success.

**Rollback/containment:** each track is independently revertable; no commit/push occurs without separate explicit approval; a restore always snapshots the pre-restore catalog first.

**Stale-plan condition:** if the target photo-genie state, the catalog schema, rusqlite/Tauri versions, or a stated assumption changes materially before execution, the writer returns `JOB_BLOCKED` "Plan stale" for re-planning or re-approval.
