### 2.1 Storage decision (binding, stated prominently)

**The storage-boundary decision is already settled by the existing schema and must be stated prominently. The normalized keyword tables are the single source of truth, and there is no flat IPTC keyword field to migrate or reconcile.**

- `keywords` table (`schema.rs:265-273`): `id INTEGER PRIMARY KEY`, `name TEXT NOT NULL`, `parent_id INTEGER REFERENCES keywords(id)`, `path TEXT NOT NULL` (denormalized full path, e.g. `"Animals > Birds > Raptor"`), `created_at`; with `CREATE UNIQUE INDEX idx_keywords_path ON keywords(path)` (`schema.rs:273`) and `idx_keywords_parent` (`schema.rs:272`). These have existed since schema V1.
- `image_keywords` join (`schema.rs:275-281`): `image_id`, `keyword_id`, `added_at`, `PRIMARY KEY(image_id, keyword_id)`, `idx_img_kw_keyword`.
- `CURRENT_VERSION = 5` (`schema.rs:17`). The `images` table has IPTC columns title/caption/copyright/creator (V1) plus the P4 V5 extended/contact fields; it has **no** flat "Keywords"/`dc:subject` column, and no migration ever adds one. There is no FTS5 table anywhere.

**BINDING DECISION:** keep the normalized `keywords` / `image_keywords` tables as the single source of truth for all keyword data. Do **not** add a flat IPTC keyword text column, and do **not** add a Keywords/`dc:subject` field to `LibraryMetaPanel` as free text — doing either would regress the existing `.lrcat` import (`lrcat/mod.rs:322-371`) and the smart-collection keyword rule (`mod.rs:1942-1948`) that already depend on the normalized model.

**Rationale:** (1) storage is already normalized and populated; adding a parallel flat field would create exactly the schema-boundary ambiguity that caused problems in P4; (2) the `UNIQUE` denormalized `path` column is the natural key used for dedupe/upsert and display; (3) catalog-only writes preserve the "never touches original files" guarantee — P5 writes keyword data to no file on disk.

**Coexistence/migration:** there is nothing to migrate. If a future phase adds XMP export of keywords (part of the deferred P4 Track E export-embedding work), it would serialize `dc:subject` FROM these normalized tables at export time; that is explicitly out of P5 scope. Folder-import `dc:subject` ingestion (Track I, Decision 3, Section 14.2, resolved to include) reads embedded `dc:subject` values out of the imported file and reconciles them into these same normalized tables using the identical case-insensitive path logic as manual create — it introduces no new column and no new table.

**Consequence:** P5 requires **no schema migration** for storage — `CURRENT_VERSION` stays at 5 (the first Library-track feature phase since P2 to add no migration). The backend-boundary changes are: (1) keyword RENAME and REPARENT must transactionally recompute the denormalized `path` of the affected node AND all its descendants and preserve the `UNIQUE`-path invariant (Section 5, Section 9, data-integrity critical); and (2) per Decision 1 (keyword-click-to-filter, Section 14.2, resolved to include), a `keyword_id` field is added to the Rust `ImageFilter` struct plus a query join — a query change, not a schema change.

**Case-sensitivity correction (binding):** the shipped index `idx_keywords_path` (`schema.rs:273`) has no `COLLATE NOCASE` and is therefore **case-sensitive**; it provides only exact-case defense-in-depth, not the case-insensitive uniqueness this plan requires. Case-insensitive sibling-name uniqueness is enforced at the **application level**: create/rename/reparent must, inside the same transaction as the write, case-fold/normalize the candidate full path (and re-derive each affected descendant path on rename/reparent) and check for a case-insensitive collision against existing keyword paths before committing, rejecting on collision. No schema migration is required for this — the exact-case `UNIQUE` index remains in place as a secondary guard.

## 4. Scope and non-goals

### 4.1 In scope (binding)

1. A hierarchical Keyword tree panel as a new fourth left-sidebar tab (`leftTab==='keywords'`, alongside Catalog/Folders/Collections), `role="tree"` of `role="treeitem"` rows, browse the vocabulary, with a non-dead-end empty-vocabulary state.
2. Keyword vocabulary CRUD: create (root or child of a selected node), rename (F2 inline), delete (app-owned `role="alertdialog"` confirmation), and reparent/move (with cycle prevention). Sibling-name uniqueness is enforced by transactional application-level case-insensitive path-collision checking (the DB `UNIQUE` index is case-sensitive and serves only as exact-case defense-in-depth), rejecting a colliding create/rename/reparent with an inline non-native error, mirroring P3's duplicate-name grammar.
3. Assign/unassign keywords to the current selection: (a) single-image via a Keywords section in `LibraryMetaPanel` — removable chips (`×` remove) plus a typeahead quick-add; (b) multi-image **batch** via a tri-state assignment surface (checked = all selected carry it / indeterminate = some / unchecked = none), applied through a single atomic all-or-nothing backend batch command — either all-succeed or full rollback with a `.pg-banner--error` + Retry; no "M of N" partial state anywhere.
4. A typeahead/autocomplete (ARIA combobox: `role=combobox` + `aria-expanded`/`aria-controls` -> `role=listbox` of `role=option` + `aria-activedescendant`; **not** native `<datalist>`) over the existing keyword vocabulary, with an inline "Create new keyword '<text>'" affordance on no-match (created as a root keyword by default, reparent afterward).
5. A new "Assign Keywords…" button in `CollectionToolbar`'s existing `role="toolbar"` selection toolbar, enabled at 1+ selected (single-image assignment is a valid common operation, unlike Sync Metadata's 2+ threshold), reusing the P4 Closure-A `.selection-toolbar__btn:disabled` opacity-0.4 styling for its disabled state, with a full keyboard-only equivalent and no context-menu-only path.
6. Keyword-click-to-filter navigation (Decision 1, Section 14.2, resolved to include): clicking a keyword filters the grid to its members with a breadcrumb chip + return-to-All-Photographs, mirroring P3's collection-as-filter navigation exactly; mutually exclusive with an active collection filter this phase.
7. Folder-import `dc:subject` keyword ingestion (Track I; Decision 3, Section 14.2, resolved to include): folder import (JPEG/PNG only, mirroring P4 Track D's `iptc_xmp.rs` scope) reads embedded `dc:subject` values from the file and reconciles them case-insensitively as root-level keywords using Track A's case-insensitive path logic, linking them to the imported image. Each `dc:subject` value is treated as a flat leaf keyword and is never split on any separator. This participates in the existing 25-file batch transaction, is idempotent on re-import, and a per-file read/parse failure is non-fatal/best-effort.

- **Data-integrity-critical finding (the P5 linchpin, analogous to P4's clobber finding):** the denormalized `keywords.path` is `UNIQUE` (`idx_keywords_path`) and is used for dedupe/upsert, display, and is the natural key. A keyword RENAME or REPARENT changes the `path` of the node AND every descendant. The implementation must recompute the `path` column for the node and all descendants transactionally and preserve the `UNIQUE`-path invariant (rejecting a move/rename that would collide). A naive single-row `UPDATE` would leave descendant paths stale and could break the `UNIQUE` index, the smart-collection keyword rule (`mod.rs:1942` uses `keyword_id`, not `path`, so that rule survives, but display/dedupe/export rely on `path`), and future lookups. This is the highest-risk item in P5.
- **Case-sensitivity finding (verified):** the shipped `idx_keywords_path` (`schema.rs:273`) is a plain case-**sensitive** `UNIQUE` index (no `COLLATE NOCASE`); it will **not** reject a case-variant sibling (e.g. "Travel" vs. "travel" would be accepted as two distinct paths). Case-insensitive uniqueness is therefore an application-level, in-transaction validation requirement on create/rename/reparent, not a property the schema provides.

A catalog that has never seen a `.lrcat` import and predates a Track I-populated folder import still has an **empty** keyword vocabulary — the empty-vocabulary UI state is a real, required first-run path, not a rare edge.

### 9.1 Track A — Keyword write-side backend (foundational; data-integrity critical)

Implement `CatalogDb` methods + Tauri commands (registered in `invoke_handler`) + devbridge routes + TS client wrappers + Rust unit tests for: `create_keyword(name, parent_id)` (compute path from `parent.path + name`; reject duplicate path); `rename_keyword(keyword_id, new_name)` (transactionally recompute path for the node AND all descendants; reject duplicate-path collision); `reparent_keyword(keyword_id, new_parent_id)` (cycle check — cannot move under itself or a descendant; recompute descendant paths transactionally; reject collision); `delete_keyword(keyword_id)` (transactional; see the Decision 2 reparent policy below); `get_image_keywords(image_id)`; and a per-keyword image-count source for the badge (assumption A1 — either extend `get_keywords` or a companion command). `create_keyword`, `rename_keyword`, and `reparent_keyword` must each perform an in-transaction **case-insensitive** path-collision check (case-folded comparison of the candidate path, and of every re-derived descendant path for rename/reparent) before committing, rejecting on collision; the DB `UNIQUE` index remains as exact-case defense-in-depth only (Section 2.1, Section 5).

**Delete policy (binding, Decision 2, Section 14.2, resolved — reparent-children-to-grandparent):** `delete_keyword(keyword_id)` reparents the deleted node's direct children up to the deleted node's own parent — so children survive one level up; if the deleted node is a root, its children become root-level keywords. This reparent changes the children's (and their descendants') denormalized `path`, and therefore reuses the same transactional path-recomputation-of-descendants and the same in-transaction case-insensitive path-collision check specified above for `rename_keyword`/`reparent_keyword`. **Collision rule (binding):** if reparenting a child up would produce a case-insensitive path collision with an existing keyword at the new level (for example, deleting "Trips" would move child "Paris" up to collide with an existing root "paris"), the delete is **rejected** with an inline non-native error explaining the collision, so the user resolves it manually (rename or move first) — never a silent merge and never a silent overwrite. The deleted keyword's own `image_keywords` rows are removed; the children's `image_keywords` links are left untouched (children, and their existing image assignments, survive). All of this — child reparenting, descendant path recomputation, the collision check, and the deleted node's own `image_keywords` cleanup — happens in one transaction.

**Acceptance:** Rust unit tests prove create/rename/reparent/delete round-trip; a rename/reparent test proves every descendant path is recomputed and the `UNIQUE`-path invariant holds; a cycle-prevention test; a duplicate-path rejection test. A Rust regression test proves a case-variant duplicate is rejected at create time (e.g. creating "Travel" when "travel" already exists as a sibling produces a rejected error, not a second row); equivalent tests prove a rename that would introduce a case-variant collision with an existing sibling is rejected, and a reparent that would move a node (or its descendants) under a parent where a case-variant path collision would result is rejected — all enforced in-transaction, not relying on the case-sensitive `UNIQUE` index. ### 9.9 Track I — Folder-import `dc:subject` keyword ingestion (Decision 3, Section 14.2, resolved: include)

1. **Parser extension.** Extend `IptcXmpData` (`iptc_xmp.rs:36-54`) with `keywords: Vec<String>`; add a `"subject"` arm to the element-text assignment logic (`iptc_xmp.rs`) that appends each `dc:subject` `rdf:li` text (trimmed, de-duplicated case-insensitively within the packet) to `keywords`. Keywords are **not** added to `to_field_updates_json` — that path stays scalar-IPTC-only; keyword population is a separate step.
2. **Hierarchy decision (binding):** each `dc:subject` value is treated as a **flat leaf keyword** — it is never split on any separator (`|`, `>`, `/`). `dc:subject` per Dublin Core/XMP is an unordered flat bag of subject terms; hierarchy is not part of its semantics. Hierarchical encoding lives in the proprietary Adobe `lr:hierarchicalSubject` field, which is explicitly out of scope for P5 (Section 4.2). Splitting on a guessed separator risks mangling legitimate keyword names that contain that character; treating the literal value as a leaf is lossless, and the user can reparent it later via the P5 reparent feature (Track A).
3. **Reconciliation/placement rule (binding):** each imported value is reconciled as a **root-level** keyword whose candidate path equals the trimmed value, using Track A's **case-insensitive** path-collision/upsert logic — not the raw case-sensitive `ensure_keyword`. If a keyword with a case-folded path equal to the value already exists at root level, it is reused; otherwise a new root-level keyword is created. This does **not** fuzzy-match against any-level leaf names, since the same leaf name can legitimately recur under multiple parents. `link_image_keyword` then ties the reused-or-created keyword to the imported image.
4. **Data-integrity model (binding):** keyword ensure/link during folder import runs inside the existing 25-file batch transaction (same connection/`BEGIN`), so within any committed batch, keyword rows, links, image inserts, and scalar IPTC commit together — no torn write inside a committed batch. This deliberately does **not** introduce a new whole-import all-or-nothing wrapper, because: (a) each file's keywords are logically independent of every other file's; (b) the shipped import model intentionally commits in 25-file batches and preserves partial progress on cancel/error (`import.rs:475-487`) — a whole-import keyword-atomicity requirement would contradict that shipped design; (c) `ensure_keyword` (upsert-by-path) and `link_image_keyword` (`INSERT OR IGNORE`) are idempotent, so re-running an interrupted import self-heals with no duplicate vocabulary or links. A per-file embedded-keyword read/parse/link failure is **non-fatal** (a warning), exactly like the shipped embedded scalar-IPTC handling (`import.rs:566`) and `iptc_xmp.rs`'s forgiving all-`None` behavior. The integrity guarantee is therefore: (i) participation in the existing batch transaction, (ii) idempotent upsert/`INSERT OR IGNORE` for safe re-import, (iii) non-fatal best-effort, and (iv) case-insensitive path reconciliation so import can never mint a case-variant duplicate.

**Acceptance:** a Rust test proves `parse_xmp_packet` extracts a `dc:subject` `rdf:Bag` into `keywords: Vec<String>` (multi-value); a test proves folder import of a JPEG/PNG carrying embedded `dc:subject` creates/reuses root keywords case-insensitively (importing "Sunset" when "sunset" exists reuses the existing keyword, no duplicate) and links them to the imported image; a test proves a mid-import interruption followed by re-import produces no duplicate keywords or links (idempotency); a test proves a file with no `dc:subject`, or an unreadable packet, is non-fatal (the image still imports, with no keywords).
