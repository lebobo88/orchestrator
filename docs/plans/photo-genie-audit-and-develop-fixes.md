## 1. Summary

`photo-genie` is a nested Git repository at `H:\CommandCenter\orchestrator\photo-genie` (its own `.git`, `main` branch, commit `233073a`), a Tauri 2 + React 18 + Vite + Zustand + WebGPU photo cataloging and development application. ### 3.3 Repository findings (grounded evidence baseline)

The following is grounded in a read-only code trace of `photo-genie @ 233073a`. All file:line references were verified during planning; they are the evidence baseline the rest of this plan cites against. Where the repository's own documentation conflicts with this trace, this section's code-level findings govern the develop-fix workstream (see the doc-discrepancy note at the end of this section, now scheduled as Phase 1.7).

**Confirmed develop-module defects (root causes):**

- **Defect A - the "Presence" group is fully dead.** Five sliders change nothing when moved: `recipe.texture`, `recipe.clarity`, `recipe.dehaze`, `recipe.vibrance`, and global `recipe.saturation`. They are written by the UI (`RightPanel.tsx:155-191`) and exist in `gpu/types.ts` (around lines 171 and 219), but no uniform builder in `src/gpu/pipeline.ts` references them, and no global shader consumes them. A grep of `pipeline.ts` and `src/shaders` confirms `clarity`/`dehaze`/`vibrance` appear only inside `mask-local-adjust.wgsl` in a per-mask context, never as global recipe fields. This is the clearest "slider does nothing" defect. An in-repo Clarity approximation reference exists at `mask-local-adjust.wgsl:226-231`.
- **Defect B - missing real fallback turns every slider into a silent no-op when WebGPU or the `float32-filterable` feature is unavailable.** `CenterViewport.tsx` only ever instantiates `WebGPUMultiPassRenderer`. `pipeline.ts:304-307` hard-throws when the adapter lacks `float32-filterable`, so `create()` returns `null` (`pipeline.ts:296-298`). `CenterViewport.tsx:128-134` then constructs no renderer at all, and the store subscription early-returns on every change (`CenterViewport.tsx:166-168`, `if (!renderer) return`). Result: on Windows WebView2 or plain Chrome lacking the feature, every develop slider is dead. This is the strongest candidate for the user's "a lot of tools/sliders don't do anything" report in the running app.

  **Concrete format/sampler grounding (verified by read, Revision 2):** the WebGPU device is requested with `requiredFeatures: ['float32-filterable']` (`pipeline.ts:307`) after the hard throw when the adapter lacks it (`pipeline.ts:304-306`). Every intermediate render pass renders to and samples `rgba32float` targets: `createFullscreenPipeline(..., 'rgba32float')` is used for White Balance (`pipeline.ts:556`), Tone (`pipeline.ts:562`), Curve (`pipeline.ts:572`), HSL (`pipeline.ts:579`), and the remaining passes; the curve LUT texture is `rgba32float` (`pipeline.ts:567-570`); mask textures are `rgba32float` (`createMaskTexture`, `pipeline.ts:409-414`). All of these are sampled with a LINEAR `bilinearSampler` (`magFilter`/`minFilter: 'linear'`, `pipeline.ts:322-325`). Linear-filtering a 32-bit-float texture is exactly the capability `float32-filterable` gates. This is the precise mechanism the Defect B decision matrix (Section 7.2, item 1.1) must resolve: either the render targets stop requiring linear filtering on 32-bit-float data, or a genuine non-WebGPU-32-float fallback path is built.
- **Defect C - an orphaned dead renderer misleads the fallback story.** `src/rendering/*` (`renderer-factory.ts`, `webgl2-renderer.ts` with exposure-only handling at `webgl2-renderer.ts:92-93`, and `webgpu-renderer.ts`) is never imported by the live rendering path. The "webgl2 fallback renders exposure only" string shown at `CenterViewport.tsx:132` points at code that is never invoked. The Defect B/C decision matrix (Section 7.2, item 1.1) resolves whether to relax/adapt the `float32-filterable` requirement (the smaller, lower-risk option) or wire a genuine multi-adjustment fallback renderer, and either integrates or deletes the orphaned `src/rendering/*` path.
- **Defect D - AI masks target the wrong image.** `MaskingPanel.tsx:171-176` calls `onTriggerAi={(m) => triggerAiMask(m, null)}`; `triggerAiMask` then calls `aiSubjectMask(imageId ?? 0)` (around `MaskingPanel.tsx:109-119`), so AI subject/sky masks always run against catalog image id 0, never the image currently open in Develop.
- **Defect E - edits are never persisted or reloaded per image.** No component calls `update_image_recipe` / `updateImageRecipe` on slider change (the `catalog/client.ts:241-247` method has no caller bound to live editing). `loadRecipe` is only called by `HistoryPanel.tsx:57` and `PresetsPanel.tsx:73`, not on image switch; the shared `getState().recipe` renders without loading the selected image's stored recipe. Edits are therefore ephemeral and shared across images rather than persisted per image.

**Ruled-out non-defect (do not "fix" this):** the AgX view-transform is effectively bypassed because `platform.loadImage` always returns `isLinear:false` (multiple lines in `platform/index.ts`), so tone edits are not double-tone-mapped. This is not a defect and Phase 1 must not change it.

**Wiring that is correct and must not be rebuilt:** the UI -> store -> pipeline -> shader chain is fully wired for White Balance, Basic tone (Exposure/Contrast/Highlights/Shadows/Whites/Blacks), Tone Curve (LUT), HSL (8 bands), Color Grading (4 wheels), Detail (sharpen/noise reduction), Lens, Geometry, and Masking raster/compose — the nine "protected groups" referenced throughout this plan. Key files: `src/gpu/pipeline.ts` (`WebGPUMultiPassRenderer`, `updateUniforms` around line 613, `render` around line 665, 10 fixed passes), `src/store/useAppStore.ts` (single store, immutable recipe updates), `src/components/RightPanel.tsx`, `src/components/CenterViewport.tsx` (subscription around lines 166-195), and `src/shaders/*.wgsl` (12 files, imported with `?raw` at `pipeline.ts:31-42`).

**Test coverage gaps:** five Vitest files under `src/__tests__` cover the store, recipe, color math, mask serialization, and the API contract, but there were no tests over `pipeline.ts`, any `.wgsl` shader, the store-to-render subscription, or any component/DOM interaction, and no deterministic render-regression oracle existed. Phase 0 (Section 7.1) closes this gap.

**Documentation discrepancy to record:** `docs/research/gap-analysis-2026-07-05.md` marks Presence (Texture/Clarity/Dehaze) and Vibrance/Saturation as "Done - verified functional" (its rows around lines 122-123), but the code trace proves they have no shader consumer. The gap-analysis "Done" statuses reflect UI presence, not render-effect verification. **Why not all Phase 2+ design routes were run in this planning pass:** the Phase 2+ scope spans roughly thirteen UI-bearing phases, several classified Standard, each independently approvable and best designed against its own concrete requirements at that phase's entry rather than in one undifferentiated planning pass. Running every design route now would substantially expand this planning pass and would pre-empt requirements that are better gathered when each phase is actually about to start. Instead, every UI-bearing Phase 2+ phase carries an explicit, mandatory, pre-classified design-gate entry criterion (Section 7.3), so phase-entry approval is an informed, scoped decision rather than a blank authorization. This is the deliberate mechanism for making design-gated phase entry explicit and unambiguous, as directed for this revision.

### 7.2 Phase 1 - Develop-module correctness (Defects A-E; sequenced first)

- **1.1 Defect B/C - measurable decision-ready resolution** (remediates J-01, J-02; user decision: no pre-commitment). A go/no-go decision matrix, executed during Phase 1 rather than decided now:
  - **Capability axis**: enumerate the target runtime matrix — Tauri WebView2 on Windows, plain Chrome, and CI/headless — and detect for each whether a WebGPU adapter exists and whether it advertises `float32-filterable`.
  - **Option 1 (relax the gate)**: remove the hard `float32-filterable` requirement and change the intermediate render-target format from `rgba32float` to `rgba16float` across all passes (WB/tone/curve/HSL/color-grading/mask/sharpen/view-transform, plus the curve LUT and mask textures). `rgba16float` is linear-filterable without the `float32-filterable` feature, preserving the linear-space HDR pipeline and the existing `bilinearSampler` usage. Trade-off to measure: 16-bit-float precision versus 32-bit — banding/quantization risk in deep shadows and wide-gamut regions.
  - **Option 2 (fallback renderer)**: wire a genuine multi-adjustment fallback (WebGL2 or a reduced WebGPU path). The existing `src/rendering/webgl2-renderer.ts` is exposure-only (`webgl2-renderer.ts:92-93`) and would need substantial work; scope this only if Option 1 fails.
  - **Go/no-go thresholds**: on the Phase 0 fixtures, compare Option 1 (`rgba16float`) readback against the `rgba32float` baseline; pass if per-region banding/error stays within a stated maximum (for example no visible contouring in the smooth gradient region beyond a stated delta-E/stepping threshold) and all Presence and tone oracles from 0.3 still pass. If Option 1 passes, adopt it (the smaller fix) and either delete or properly integrate the orphaned `src/rendering/*` path (Defect C) to remove the misleading "webgl2 fallback renders exposure only" message (`CenterViewport.tsx:132`). If Option 1 fails banding, evaluate Option 2 against the same oracles.
